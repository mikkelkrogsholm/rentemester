# R03: Define exact money, schema, audit and wire compatibility

<!-- rentemester-rust-plan:R03 -->

Parent epic: #672. Phase: P0 — Inventory and binding design decisions. Status: planned.

## Outcome

Resolve numeric and persistent-format compatibility before selecting Rust representations or enabling readers/writers.

## Scope

- Document supported SQLite/control-schema versions, triggers, constraints, migration checksums and read-only snapshot behavior

- Define monetary bounds, currency scale, rounding, FX rates, dates, identifiers, JSON encoding and canonical hash/signature bytes

- Decide additive/versioned API changes for existing JSON-number clients versus exact-string clients

- Specify preservation or explicit mapping of stable principal, workspace/company/ledger identities and idempotency receipts/tombstones across credential rotation, re-enrollment and local/server transfer.

## Dependencies

- Requires #673 — Freeze the migration baseline and complete the feature/contract inventory

## Acceptance criteria

- [ ] Synthetic cross-language vectors cover boundary/overflow, negative/tie rounding, dates, Unicode, null/omitted fields and historical canonicalization

- [ ] Legacy hashes/signatures validate without rewriting old audit history; incompatible formats fail closed

- [ ] An explicit compatibility matrix defines schema direction, old-client behavior and rollback constraints

- [ ] A lost-response mutation retried after credential/host migration cannot execute twice; unsupported identity mapping blocks cutover rather than inventing a new scope.

## Verification and completion

Attach actual revision-bound checks for the criteria above, including the stated refusal/failure paths. Refine typed contracts, risk/error scenarios and data effects before implementation; the planning graph is a sketch, not proof of readiness or behavior. Record any unsupported environment or external dependency as a blocker rather than lowering acceptance.

## Boundaries

No live migration or unrelated new product capabilities. One authoritative writer per workspace; company-specific data stays in workspace configuration; checked-in acceptance data is synthetic. Preserve existing accounting/security/release gates. No live use before the cutover gate.
