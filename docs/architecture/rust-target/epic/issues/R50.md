# R50: Complete remote desktop login, profiles and reconnection

<!-- rentemester-rust-plan:R50 -->

Parent epic: #672. Phase: P5 — Agent, web and desktop interfaces. Status: planned.

## Outcome

Make the same installed app a reliable client of a server-owned workspace.

## Scope

- Integrate native auth, per-server accounts, credential stores and capability-aware profile selection

- Show active server/company clearly and cancel/invalidate old-context reads

- Implement reconnect/read-back and safe logout/revocation without offline mutation queues

## Dependencies

- Requires #712 — Implement hosted identity, native login and service-principal lifecycle

- Requires #715 — Implement the Rust API client and connection-scoped caches

- Requires #719 — Build the GPUI local shell and managed backend lifecycle

- Requires #720 — Build GPUI read workflows, reports and evidence inspection

## Acceptance criteria

- [ ] Web and desktop show the same server ledger after permitted writes

- [ ] Changing server/account/company during pending requests cannot leak data or execute under stale context

- [ ] Lost responses use the R05 operation-specific key/read-back/provider reconciliation; server unavailability never creates local accounting effects.

- [ ] After a verified move, the active destination and moved/read-only source are visible; reconnecting an old source cannot look like continuing the authoritative accounting workspace.

## Named owner acceptance scenarios

### J03 — Remote multi-user operation and access loss

Given: Hosted workspace, two companies, owner/bookkeeper/service identities.

When: Log in web/native, switch company, review/post, revoke access during a pending read/write.

Then: Same authoritative ledger, visible server/company and role-correct actions; no cross-company/stale-cache disclosure or local fallback.

### J06 — Local-to-server and server-to-local handoff

Given: A supported synthetic workspace with an accepted write whose response was lost, plus pending/ambiguous external effects.

When: Stop/fence source, verify transfer, map identity/receipts, activate destination, retry original operation and reopen old source.

Then: One writer/dispatcher, no duplicate booking/delivery, replay obeys access policy; owner sees destination and moved/read-only source.
