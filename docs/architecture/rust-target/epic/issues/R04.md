# R04: Resolve hosted/native identity and cross-database authorization ordering

<!-- rentemester-rust-plan:R04 -->

Parent epic: #672. Phase: P0 — Inventory and binding design decisions. Status: planned.

## Outcome

Choose a supported identity approach and an enforceable revocation/commit ordering before porting authenticated writes.

## Scope

- Compare retaining Better Auth during transition with the eventual supported Rust-hosted identity design

- Specify browser/native login, MFA/recovery/reset, service principals, credential migration and re-enrollment where required

- Define linearization/fencing for membership revocation versus company-ledger commit and process-crash recovery

- Specify execution authority and revoke/cancel/lease/dispatch ordering for already committed external jobs, including provider-consent changes, crash and restore.

## Dependencies

- Requires #673 — Freeze the migration baseline and complete the feature/contract inventory

## Acceptance criteria

- [ ] A decision record selects implementable identity and synchronization contracts with threat model, revocation ordering and failure semantics

- [ ] Existing MFA/recovery/session/last-owner/service-account protections are explicitly preserved

- [ ] A temporary TypeScript identity dependency has a named removal gate and cannot satisfy the all-Rust-backend exit criterion

- [ ] Decision tables cover revoke before dispatch, during an external call, after lease expiry and after restore; committed job history does not silently grant permanent future authority.

## Verification and completion

Attach actual revision-bound checks for the criteria above, including the stated refusal/failure paths. Refine typed contracts, risk/error scenarios and data effects before implementation; the planning graph is a sketch, not proof of readiness or behavior. Record any unsupported environment or external dependency as a blocker rather than lowering acceptance.

## Boundaries

No live migration or unrelated new product capabilities. One authoritative writer per workspace; company-specific data stays in workspace configuration; checked-in acceptance data is synthetic. Preserve existing accounting/security/release gates. No live use before the cutover gate.
