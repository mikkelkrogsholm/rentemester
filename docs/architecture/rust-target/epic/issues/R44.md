# R44: Port the CLI, local launcher and machine-readable contracts

<!-- rentemester-rust-plan:R44 -->

Parent epic: #672. Phase: P5 — Agent, web and desktop interfaces. Status: planned.

## Outcome

Retain stable automation and explicit local/server operation in Rust.

## Scope

- Port all R01 command keys, help/examples, actor/config policy, exits and output envelopes

- Support explicit local company/workspace and remote connection selection without hidden company defaults

- Make local ownership, stdin/files, cancellation and destructive confirmations consistent

## Dependencies

- Requires #677 — Specify versioned API, typed failures and capability negotiation

- Requires #687 — Port atomic posting, reversal, idempotency and shared mutation gates

- Requires #707 — Port backup, restore, signatures and workspace transfer

- Requires #714 — Implement the Rust HTTP server and operational API pipeline

- Requires #715 — Implement the Rust API client and connection-scoped caches

## Acceptance criteria

- [ ] Contract fixtures cover 0/1/2 exit semantics, flags, JSON/human output and refusal codes

- [ ] Local CLI joins the owning runtime or refuses competing writes; remote actors derive from credentials

- [ ] Existing scripts have a documented compatibility path; unsupported operations are discoverably unavailable

- [ ] Per-operation fixtures preserve bare arrays, flat write results, snake_case, stdout/stderr and exact 0/1/2 exits, including CLI-only operations; standardization requires versioned compatibility.

## Verification and completion

Attach actual revision-bound checks for the criteria above, including the stated refusal/failure paths. Refine typed contracts, risk/error scenarios and data effects before implementation; the planning graph is a sketch, not proof of readiness or behavior. Record any unsupported environment or external dependency as a blocker rather than lowering acceptance.

## Boundaries

No live migration or unrelated new product capabilities. One authoritative writer per workspace; company-specific data stays in workspace configuration; checked-in acceptance data is synthetic. Preserve existing accounting/security/release gates. No live use before the cutover gate.
