# Purpose-bound native email verification token

The configured source signs verification JWTs with HS256 using the original active secret string, lowercased email, integer issued-at and one-hour expiry. It does not use the retained MFA encryption keyring, store a token context or prevent replay. This prerequisite adds native crypto only: no HTTP, database issuance/consumption, mail, verified user, membership, MFA or session authority. The full email-verification flow remains the next required work; the Rust epic is unchanged.

Native tokens retain source-readable HS256/email/iat/exp and add mandatory purpose=rentemester-email-verification-v1, trusted workspace and256-bit random jti. Native verification accepts only that envelope under the configured current key/workspace. No legacy stateless token adoption, rotation fallback, email change updateTo/requestType, generic JWT or other purpose is accepted. Each issuance samples a trusted Clock once; iat=floor(ms/1000), exp=iat+3600. Verification samples once and requires iat<=now<exp with exact one-hour lifetime and finite calendar bounds. It verifies the raw compact signing input with constant-time HMAC comparison before accepting claims, rejects padding/noncanonical base64url/extra segments/duplicate or unknown JSON fields, wrong types, oversized data, algorithm/header confusion and malformed nonce. Errors are fixed AuthError variants, never bearer/claim/parser text.

Signer, bearer and verified metadata omit Debug/Clone/Serde; owned key, token and decoded claims are zeroizing where supported, without universal parser/library/allocator copies or whole-operation constant-time claims. Verified metadata is a crypto observation, never an authenticated principal. It binds to signer workspace and key and exposes email, nonce, time and a token digest for the future admitted writer. Email here is a bounded lowercase ASCII coordinate, not a user lookup, deliverability decision or the storage layer's complete email policy. Future use must validate the canonical current user/email and native issuance context under a writer, enforce single consumption/revocation/history and distinguish known/unknown commit before redirect or mail. Signature validity alone must never mark an email verified.

Acceptance uses native strict-boundary tests plus installed jose/source JWT oracles in both directions, HMAC mutation controls, same-second random issuance, exact expiry/future/lifetime, key/workspace/purpose separation and forbidden legacy/change-email envelopes. Existing native identity tests remain unchanged. Scoped GDD is structural readiness for this crypto primitive only. HTTP callbacks, persistent one-time context, actual mail, issuer/recipient policy, current-user transaction, deployments and full R04/R41/R42 acceptance are not qualified.

Integration review requires fresh time validation under writer admission: accepts(proof) binds only workspace/key and cannot certify later freshness. The legacy /verify-email handler accepts the native envelope but ignores its extra context claims. It must not remain an authoritative verification writer alongside native routes; wire/crypto interoperability is not safe dual-endpoint qualification. Native one-time context and legacy-route closure must ship together before enabling actual verification.
