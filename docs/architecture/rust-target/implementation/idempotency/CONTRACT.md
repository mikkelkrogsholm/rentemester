# Native durable keyed mutation receipts

Port `src/core/idempotency.ts` keyed local receipt behavior into a caller-owned main write transaction, suitable for the existing control→company authorization fence. This increment owns storage receipt execution, JSON fingerprints, source interoperability and failure/concurrency checks. Actual manual post/reverse, service company admission, physical lifetime admission, transport endpoints and complete R14 acceptance remain required. Only synthetic disposable data is used.

The trusted application must authorize the current principal and operation before invoking the primitive, including before replay; input principal and actor are internal facts, never authenticated request claims. The primitive accepts only the seven existing key-idempotent operation names, an explicit user/service-account subject, actor/program, validated business JSON object, mandatory validated client key, and trusted UTC milliseconds. Caller must already admit canonical company schema/physical identity and own a main SQLite write transaction. No connection, transaction, authority or migration is acquired here. Any primitive error requires rollback of the entire caller transaction, including result-shaped `ok:false`; the rejection value is retained for the application. The existing fence releases values only after known commit and retires uncertain handles.

Receipt identity is SHA256 of the original UTF8 key, current immutable ledger UUID, operation, principal kind and exact stable subject. Key validation follows JavaScript UTF16 length1..128 and ECMAScript trim nonemptiness without trimming the stored key. Actor, program, credential, path and workspace/company display selectors are excluded. Actor/program use ECMAScript trimming before source audit rendering; explicit actor/program input bounds are512/256 UTF8 bytes and empty components refuse. Payload fingerprint recursively sorts object keys by UTF16 code units, preserves array order, uses JSON.stringify-compatible strings and correctly rounded binary64 parsing (`serde_json/float_roundtrip`) and number rendering, and hashes at most65536 UTF8 bytes. Business payload must already exclude transport confirm/idempotencyKey. Native typed boundary rejects unsafe integer-valued JSON numbers, nesting beyond64, lone surrogates and non-object business roots; these explicit stricter refusals do not reinterpret source receipts.

Under the held writer, lookup precedes all domain effects. Same identity and same fingerprint replays the stored JSON outcome and original receipt metadata with a new idempotency_replay audit. Changed fingerprint produces IDEMPOTENCY_CONFLICT before checking outcome presence. A missing outcome produces IDEMPOTENCY_OUTCOME_EXPIRED, even if its expiry is future. Both refusal audits may be committed only by a caller which has performed no domain effects and deliberately retains the diagnostic; rolling back removes the audit. Clock expiry alone does not suppress a retained outcome: source retention deletes replay material explicitly. Replay never invokes the domain callback.

Fresh execution invokes synchronous trusted transaction-local Rust code once. Outcome objects may have different property order in serialized JSON; parsed JSON values and source fingerprint bytes are the interoperability contract. Successful domain JSON, append-only tombstone, outcome and idempotency_original audit belong to the same caller transaction. `ok:false`, callback errors, oversized/invalid outcomes and SQL/audit failures are errors requiring whole-transaction rollback, leaving the key reusable. Receipt expires30days after the trusted timestamp. Source-compatible audit event/entity/message/actor fields are retained. No raw key is stored in any receipt or audit. Both generated tombstone and audit IDs use explicit checked positive JavaScript-safe MAX+1; exhausted/poisoned streams refuse rather than SQLite random fallback.

Pruning requires the same admitted main writer and deletes only outcomes whose tombstone expires_at<=trusted canonical UTC cutoff. Tombstones and ledger identity remain unchanged and their source triggers remain authoritative. Strict native stored metadata validation rejects malformed ledger UUIDs, receipt IDs, payload hashes, timestamp pairs, duplicate identity matches, oversized/malformed/rejection outcomes and incomplete expiry duration before replay. Malformed metadata is a storage refusal, never a cache miss or new operation.

Acceptance compares actual installed source executor and native executor on canonical synthetic company DBs: key/Unicode/numeric canonicalization, new/replay/conflict/pruned and retained expiry behavior, principal/operation/ledger isolation, key rotation/actor/path independence, business rejection and late SQL rollback, immutable tombstones, bounded IDs, actual concurrent same-key writers and process death before commit. Compose with the real current human authorization fence to prove revoked replay does not invoke receipt lookup or disclose outcomes. Source-generated receipts must replay natively and native receipts must replay through the source implementation. These checks qualify storage composition, not a deployed posting endpoint or full engine completion.
