# Native password-reset completion

`password_reset::execute` completes an existing Better Auth 1.7.1 `reset-password:<token>` record on the caller's admitted current control connection. Its only recovery authority is possession of the exact current bearer and its unique unexpired database row. It accepts no requested subject, account ID, membership claim, session or MFA proof. The runtime injects Clock and audit-key version. Actual physical handle/workspace lifetime admission and public origin/rate/bounded-blocking dispatch remain prerequisites before exposing it. It issues no reset link, sends no mail, redirects nowhere and grants no session or cookie.

Preflight rejects an unready connection before input/KDF work. Token grammar is exactly the source generator's 24 ASCII alphanumeric characters, case-sensitive, without trimming/percent decoding. The original password must contain 12–128 UTF-16 code units, before shared NFKC/scrypt derivation; spaces are preserved. Six supplementary scalars count as twelve code units. Rust strings cannot represent isolated JavaScript surrogates; those are outside this native input contract. Shared crypto budgets and OS entropy apply. No request-derived subject or pre-KDF database snapshot authorizes later changes.

The new salted hash is derived with no SQLite transaction or writer held, including for syntactically valid but absent tokens. Only afterward does BEGIN IMMEDIATE acquire the one admitted writer. One trusted clock sample supplies expiry decisions and canonical millisecond UTC mutation/audit timestamps; accepted range is 0 through 253402300799999. The audit-key version is a nonnegative JavaScript-safe integer. The writer admits exact current schema/history and resolves the token anew, so deletion or successful consumption during unlocked KDF cannot be bypassed.

Exactly one verification row must match the complete identifier under binary comparison. Missing tokens or missing referenced users refuse opaquely. Duplicate identifiers, malformed/nonblank/control/4096-byte-bounded row IDs or subjects, noncanonical UTC timestamps, createdAt > updatedAt, updatedAt > now, expiresAt <= createdAt, or a lifetime over one hour refuse. Native expiry is strict: expiresAt must be greater than now. Rejected operations do not delete expired or ambiguous rows; confirmed rollback preserves them. A reset is allowed for an existing disabled, unverified, nonmember or MFA-disabled user, without old-password or MFA-keyring dependency; this never changes access or verification state.

The canonical credential key is (issuer='local:credential', accountId=subject). Its existing owner must be that subject and providerId must be 'credential'; a conflicting foreign owner/provider refuses without adopting or overwriting it. An existing credential retains ID, createdAt and all other provider fields while only password/updatedAt change. A missing canonical credential is created with fresh OS-random ID and exact local provider fields. Other provider accounts are untouched. A null/malformed old password does not prevent legitimate reset; no old password is verified. User, factor, backup codes, factor lock budget, replay state and membership rows are unchanged.

Success deletes every `reset-password:` verification row whose value is this exact subject, including outstanding sibling links, and all this subject's session rows, including expired/malformed-time rows. Other subjects and verification namespaces are preserved. A user cannot reuse an older recovery link after native recovery. Native pending MFA/enrollment context remains stored but its credential fingerprint and actual credential_updated/session_deleted lifecycle observations make prior context unusable where such a credential context existed. Credential insertion has no canonical credential_updated trigger and no such event is fabricated. No claim is made that source in-flight two-factor/trusted-device flows are fully revoked by this implementation.

One writer transaction contains credential mutation/creation, all link consumption, all session deletion and its canonical session_deleted/credential_updated triggers, native workspace audit and accepted reset-password telemetry. The workspace_audit event is password_reset_completed / native_password_reset_v1, actor user:<subject>, with a JSON tuple of subject, audit-key version, credential-created boolean, deleted-session count and consumed-reset-row count. Telemetry includes only fixed endpoint/outcome, subject, version and trusted timestamp. Neither audit contains email, raw token, URL, hash, password, provider token or display metadata. Returned success is unit only after known commit. PasswordHash is zeroized on drop; identifiers built from the token are zeroized. Caller owns input and transport buffers.

A pre-commit error explicitly rolls back and reports NotCommitted with connection reuse only after successful rollback and readiness check. Any commit error reports OutcomeUnknown, retires the handle and withholds success. Observing an old image after closing a busy test connection does not strengthen that guarantee into universal rollback. Do not automatically replay an uncertain reset or promise the client its old password is still valid; reconcile current state or initiate a new recovery through the eventual delivery flow. This increment sends no external effects and exposes no endpoint.

The installed source consumes its latest matching row (and all duplicate identifiers) before KDF and subsequent mutations, accepts expiry equality, deletes expired values while refusing, and leaves sibling reset links valid. Native deliberately strengthens this into one atomic transaction, refuses duplicate/malformed/oversized-lifetime records, uses strict expiry and revokes sibling links. These are documented versioned corrections rather than byte-for-byte endpoint parity. Current source has no secondary verification storage or identifier hashing configured. Different configured token lifetimes/storage/identifier formats require separate qualification.

Acceptance uses synthetic canonical current control copies in WAL/DELETE, actual installed source request token issuance with an in-memory email sink, source/native hash and login readers, existing and absent canonical credentials, foreign provider/owner boundaries, original UTF-16 length/NFKC, strict token/time/schema/config refusals, preserved access/MFA state, one-time/sibling consumption, full rollback, separate-process writer contention, unlocked-KDF token deletion and real commit-busy at creation/update. Full native and Rust integration regression, scoped GDD readiness and read-only review bind evidence to actual source hashes. No real company/user data, production mail or deployment is involved.
