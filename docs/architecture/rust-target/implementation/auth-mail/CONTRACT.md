# Native HTTP JSON v1 auth-mail transport

HttpJsonAuthSender implements the existing ResetSender and exposes one explicit MailKind (verification/password-reset/workspace-invitation) delivery operation for the existing auth-mail gateway. It is a concrete blocking HTTPS client, with no database or background delivery queue. Reset requests call this port only after their separately verified known commit. A successful transport result confirms gateway handoff, not end-user receipt, and a failed result can follow actual acceptance. Existing reset-request Committed/auth_delivery_unconfirmed semantics and future public acknowledgement concealment remain binding.

GatewayConfig is injected operator configuration: HTTPS endpoint, bearer token, from address and HMAC idempotency secret, with no environment secret/host/proxy fallback. Configuration/sender/message types expose no Debug/Clone/Serde secrets. Endpoint is at most 4096 bytes and excludes query, fragment, nonempty credentials, backslashes, wildcard host and controls. Bearer is nonblank trimmed ASCII, at most 4096 bytes, and must form a valid header; its HeaderValue is marked sensitive. Original from input is bounded to 4096 bytes, trimmed for the outgoing payload and checked against the source practical non-whitespace one-at/dotted-domain grammar. Valid Unicode addresses remain supported. Idempotency secret is nonblank, control-free and at most 4096 bytes; original UTF-8 bytes, including internal spaces/non-ASCII, are retained.

One compact JSON request uses exactly version=rentemester-auth-email-v1, kind, to, from, subject, text and actionUrl. All three source Danish subject/text templates and kind values are preserved. The four explicit headers are authorization=Bearer <injected value>, content-type=application/json, idempotency-key=<lowercase hex HMAC-SHA256>, and x-rentemester-auth-event=<kind>; normal HTTP framing headers are supplied by the client. HMAC input is rentemester-auth-email-v1, NUL, kind, NUL, token using configured secret UTF-8 bytes, exactly as the source. Same-kind/same-token retries reuse both the serialized bytes and key; different tokens/kinds produce independently scoped keys. No raw token is added as a JSON field.

Recipient is nonblank, control-free, at most 4096 bytes and satisfies the practical email grammar without trimming. Token is nonblank/control-free and at most 8192 bytes; generic mail supports existing verification/invitation token formats, while ResetSender receives the already validated native 24-alnum reset message. Action URL is bounded to 16384 bytes, parsed HTTP(S), has a host and excludes nonempty credentials/backslash/controls. Final serialized JSON must not exceed 32768 bytes. These are delivery-input checks, not authorization of an email, invitation or recovery action; the relevant use case must validate the subject/action before constructing a message.

Construction validates configuration and creates the reusable client. Domain endpoints load the system DNS configuration once at construction using direct pinned Hickory; configuration acquisition errors fail InvalidConfig. Hickory also loads the hosts file at construction on a best-effort basis, substituting empty hosts if that read fails. IP endpoints need no resolver. The custom async resolver uses only that prepared configuration, without lazy system lookups, getaddrinfo or implicit public-resolver fallback. This specifically corrects reqwest's default Hickory lazy initializer, which could block on system configuration and fall back to Google DNS. Configuration/hosts acquisition and client startup are outside the delivery-time budget. Changes to system DNS configuration require rebuilding the configured sender.

TLS uses reqwest 0.13.5/rustls and the pinned Mozilla webpki-root-certs 1.0.9 roots with certificate and hostname validation. Explicit roots bypass the platform certificate verifier and its possible synchronous OS/network work. Production offers no invalid-certificate/name bypass or test-root injection. Private/OS-added trust roots, OS revocation policies, root-store maintenance, other TLS backends and platform qualification need explicit release/deployment decisions; bundled roots do not update without a new build. The ignored synthetic process helper alone can substitute an ephemeral local CA and DNS server, using the same validated client policy and delivery code.

The client is HTTPS-only, HTTP/1, with redirects, automatic referrer, proxies (including environment/system proxy), cookies, decompression, verbose wire logging, TLS key logging and reqwest-internal protocol retries disabled. It allows at most 64 HTTP/1 response headers; the HTTP dependency's bounded parser buffers remain in force. Only the response status is inspected, and the body is dropped without parsing, logging or draining an unbounded response. No action URL is fetched: only the configured gateway endpoint receives a POST. Redirects never forward credentials or mail content, even within the same origin. Supporting a required proxy, private roots or HTTP/2-only gateway needs a separately specified configuration, not an implicit fallback.

Delivery starts one monotonic Instant budget of eight seconds before input/serialization work. Each of at most three attempts gets only the remaining timeout. Any 2xx before budget expiry acknowledges handoff; 429 and 500–599 permit retry, other HTTP statuses stop immediately, and transport/TLS/DNS errors permit bounded retry. Backoff is 100ms then 200ms, clipped to remaining budget; it does not honor Retry-After or generate another message/token. The same body/key are retained throughout. No attempt starts after exhausted budget. Timed-out DNS or response futures are canceled by the client request timeout. Scheduling delays, synchronous system configuration/client construction, client destruction's runtime-thread join and whole-server worker admission are outside this ordinary-scheduling delivery budget; this is not a hard realtime or universal process-shutdown guarantee.

Failure is the fixed opaque DeliveryUnconfirmed only. Raw transport/provider errors, response bodies, addresses, endpoint paths, tokens, URLs, headers and keys are not added to errors or logs by this module. It installs no logger. Authorization headers are sensitive and owned HMAC key/body buffers are zeroized; reqwest/TLS/URL/header/body copies and caller inputs are not universally zeroized. Application-wide dependency tracing and platform crash/storage qualification remain release gates. Gateway acceptance is not proof of final delivery, revocation, database rollback or safe automatic new-token retry.

The source gateway has the same normal wire/templates/HMAC, three-attempt network/429/5xx behavior and eight-second wall-clock budget. Native intentionally uses a monotonic budget, explicit parser/input bounds, stricter endpoint query/credential restrictions, prepared fail-closed async DNS, pinned roots, disabled redirects/proxies/keylogging and no hidden retries. These are documented source corrections. Existing source runInBackgroundOrAwait may swallow a sender rejection; native transport returns uncertainty to the use case, whose failure/public acknowledgement rules are separate.

Acceptance uses real ephemeral local CA/leaf TLS servers and a synthetic UDP DNS server, with the installed TypeScript sender as an in-memory independent body/header/HMAC oracle for all three kinds and Unicode input. Cases cover same-body/key retries and token separation, 2xx/4xx/429/5xx decisions, no redirect forwarding, environment proxy/keylog refusal, untrusted-root and hostname refusal, network disconnect attempts, genuinely stalled TLS-response and unanswered-DNS budgets, actual async hostname/SAN lookup, input/body limits and the concrete native ResetSender trait. All mock listeners bind loopback, private keys live only in temporary test files, and no external email/gateway is contacted. Full Rust regression, scoped GDD structural readiness, runtime typecheck/lint and independent review bind evidence to the exact final sources.

This increment does not expose public auth HTTP/CLI/MCP/UI endpoints, qualify actual SQLite/workspace lifetime ownership, provide durable outbox/guaranteed delivery, finish email-verification/service/trusted-device/provider identity, migrate real users/companies, deploy production, distribute the app or qualify cutover. Dependency and root updates/platform behavior remain part of the full release requirements.
