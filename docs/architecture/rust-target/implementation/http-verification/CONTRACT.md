# Native HTTP email verification

AuthHandlers now has optional VerificationHandlers for native persisted request/completion operations on caller-admitted control handles. Its canonical /api/auth/send-verification-email and /api/auth/verify-email paths never dispatch to a legacy handler. With no verification handlers, POST/GET fail closed with 404; HEAD always refuses without consuming a token. The serving owner must route these paths exclusively to Rust and drain the old authoritative verify-email writer before enabling a real deployment. This library/synthetic socket qualification does not close an independently running TypeScript endpoint or qualify physical/lifetime admission, migration or production rollout. The full epic remains open.

POST send-verification-email requires exact configured Host/Origin, admitted fetch metadata, JSON content, no service/Authorization credential, bounded nonduplicated Cookie header, no query, an 8 KiB body and the existing body deadline. Its strict object accepts only email and optional non-null callbackURL; duplicate/unknown fields, invalid email or unsafe callbacks refuse before native dispatch. Optional session-cookie parsing ignores unrelated cookies but rejects malformed, duplicate or wrong-profile named session credentials, including a bare session-cookie name beside a valid signed value. A signature is only a caller proof; native request processing rechecks the current session/address under its writer. Pending challenge cookies create no session authority.

After admission, the existing shared worker permit stays inside blocking work through completion even when the HTTP caller disconnects. Every handler outcome, including unknown commit, delivery error and panic, returns the same 200 {status:true} acknowledgement with a 500 ms minimum after input validation. No bearer, existence, delivery or success assertion is returned. The floor and equal response do not prove constant-time privacy when mail takes longer, and the injected handler must remain bounded. The native application controls real commit/delivery semantics and never automatically reissues a link. The POST rate is three per direct-peer IP per minute, sharing bounded rate/capacity state with identity/recovery; forwarded headers and email/token rotation do not create rate identities. Persistent/distributed/proxy policy remains a separate deployment qualification.

GET verify-email permits originless cross-site mail navigation but requires exact Host, an actual direct peer and any presented Origin to match. Authorization/service credentials refuse. Query is bounded, accepts only one original compact token and optional callbackURL, rejects percent-encoded token aliases, unknown/duplicate keys, invalid percent/UTF-8 and unsafe callback destinations, and decodes callback exactly once. Callback success processing is validated before native mutation. A fixed operation rate of ten per peer/minute does not use the bearer as a key. HEAD does no dispatch or rate consumption. Tokens signed by the actual source without native context and correctly signed but unissued native envelopes both refuse; there is no source-handler fallback.

Only a known native completion returns 200 {status:true,user:null}, or 302 to the prevalidated/sanitized allowed callback. No session/cookie is created. Native invalid/expired/replayed/unissued tokens normalize to 401 INVALID_TOKEN or a fixed error callback. Unknown commit, internal failure and panic yield 503 VERIFICATION_UNCONFIRMED or an error callback; they never yield a success destination. The callback helper inserts no verification bearer and removes reserved token/error/verified query coordinates, preserving other user values/fragments. Responses use no-store/no-referrer/nosniff. General listener/header/TLS/shutdown and host panic-log redaction are not newly qualified here.

React shows fixed recovery guidance for INVALID_TOKEN, TOKEN_EXPIRED and VERIFICATION_UNCONFIRMED callback errors, removes the consumed error from browser history, and does no automatic login/resend. Anonymous and authenticated resend explicitly disable request retries and retain the same conditional generic messaging for success, rejected acknowledgement and transport loss; neither claims that mail was sent. The authenticated product state still comes from normal session/product reads, never a query flag.

Acceptance uses real native sockets plus current synthetic control schemas in WAL/DELETE, actual source cookie/JWT signers, digest/flag/session/audit observations, strict input/query checks, HEAD/replay controls, direct-peer rate checks and actual busy/unknown commits. Native unit tests also inject precommit/unknown/committed/panic outcomes and verify generic timing/body plus fixed callback mapping. UI tests cover recovery without side effects. No external mail, real company data or deployment is used. Scoped GDD is structural readiness only. Remaining service/provider/trusted-device identity, product context, workspace lifetime/legacy writer/restore-lineage qualification, clients/platform/distribution and cutover remain required.
