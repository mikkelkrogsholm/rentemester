# Native verification mail and completion destination

This increment composes persisted one-time verification with message preparation, an optional current caller, postcommit mail and a trusted completion destination. It does not register or enable native HTTP routes. Public acknowledgement/session-cookie parsing/timing/rate policy and closing the authoritative legacy verify-email bypass remain required before enablement. The complete Rust epic is unchanged.

The request runtime receives an admitted control connection, trusted token signer/Clock/audit version, cookie verifier and RecoveryLinks origin allow-list. Connection preflight precedes disabled-sender, invalid-input or connection-reuse claims. Disabled delivery refuses before issuance. Canonical email validation, optional caller recheck and full bounded message preparation happen inside the issuance writer. Caller proof must belong to the configured cookie verifier and signer workspace; the current canonical unexpired session must still resolve to that exact email under the writer. It grants no workspace access, MFA or new session. Anonymous unknown/already-verified recipients return the same unit acknowledgement and create no intent or mail. Account existence and internal failure stages must be concealed by the future public mapper.

The message URL uses the configured base origin and /api/auth/verify-email with original token and callbackURL query parameters encoded by the URL library. Missing/empty request callback defaults to /. The existing strict origin/redirect policy is shared with recovery: secure configured origins, loopback-only HTTP development, no credentials, control characters, wildcard origins, backslash or protocol-relative escapes. Recipient/token/action URL are bounded; a message that would exceed the gateway URL budget is rejected before commit and its tentative intent rolls back. VerificationMessage owns zeroizing recipient/token/URL buffers and has no Debug/Clone/Serde, without claiming elimination of all library/parser copies.

Only a known successful issuance commit releases an optional prepared message. Sender is called with no SQLite transaction held. The concrete HTTPS gateway uses the existing verification subject/wire shape and token/kind HMAC idempotency key; its bounded retries reuse identical token/payload/key. The application never automatically reissues a new token. A mail error may follow actual delivery, so it returns Committed/auth_delivery_unconfirmed and retains the original usable link. Unknown commit retires the handle and calls no sender; precommit failures roll back and require successful rollback/preflight before reuse. Injected sender ports must be bounded; sender panic or caller cancellation cannot be treated as proof that committed effects were canceled.

Completion validates and constructs the successful destination before attempting the email flag mutation. It returns that destination only after known completion; omitted/empty callback yields None for a future JSON response. No verification bearer is injected into a callback, and reserved token/error/verified query coordinates are removed. Other caller-supplied path/query values and absolute URL fragments are preserved. The pure callback helper can add only fixed INVALID_TOKEN or VERIFICATION_UNCONFIRMED errors for the corresponding trusted result; unknown commits never produce the success destination. Existing one-time/current-context/flag/audit invariants remain in force, without automatic sign-in.

Acceptance uses canonical synthetic control schemas and separate native processes in WAL/DELETE modes: digest visible before unlocked delivery, generic unit acknowledgement for absent/verified recipients, exact destination/default handling, invalid/oversize URL rollback, disabled sender, delivery uncertainty without reissue, current caller mismatch/expiry/revocation/workspace checks, revocation during unlocked preparation, stale link after postcommit credential change, late SQL rollback and real unknown commits for request/completion. A local HTTPS fixture exercises the actual VerificationSender implementation and compares its JSON/idempotency HMAC with the installed source sender. No external mail or real data is used. GDD readiness is structural evidence for this scoped composition only.

Next work is the native send-verification-email/verify-email HTTP boundary, generic public response and timing/rate/caller-cookie rules, socket/source/UI checks and coherent routing that cannot fall back to the legacy verification writer. Current Rust operations are not production admission or permission to run two authoritative verification handlers. Full physical/lifetime writer and restore-lineage qualification, remaining provider/service identity, engine/client/platform/distribution parity and cutover remain required.
