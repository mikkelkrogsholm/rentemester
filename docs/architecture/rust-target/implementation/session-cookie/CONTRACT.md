# Native current-cookie authentication under the control fence

This R04/R13/R41 increment verifies the installed Better Auth 1.7.1 signed opaque session cookie in Rust and resolves its current database session inside the existing control-to-company fence. It does not implement login, password/MFA/recovery/reset/enrollment, service credentials, CSRF, a server endpoint or live writer admission. Better Auth issuance remains transitional; R41/R55 cannot close until complete native identity flows replace its Bun/TypeScript runtime and all migration/security gates pass. No new password or identity scheme is introduced.

The runtime verifier is explicitly configured with a workspace key, Secure or development cookie profile and the canonical injected active secret (unpadded base64url encoding of at least32 random bytes, as existing Rentemester config requires). HMAC uses that secret's UTF8 STRING bytes, not its decoded entropy. Better Auth's current active secrets[0].value signs/verifies session cookies; old versioned/legacy secrets are not cookie fallbacks. No environment key/default or claimed actor is consulted. Supported names are __Secure-better-auth.session_token and better-auth.session_token according to the explicit profile. Reject wrong profile, duplicate/ambiguous session cookies, missing token, malformed percent/UTF8 encoding, noncanonical44-character standard-base64 signature, invalid MAC or headers exceeding8192 bytes. Generic/cache cookies confer no authority. Optional quoted cookie syntax and percent decoding follow the emitted wire; decoded token is exact and bounded to512 bytes, nonempty and contains no control characters. Signature comparison uses maintained constant-time HMAC verification. Any presented service-key header is refused by this human-only path, including empty values; a dedicated later service adapter must handle services without cookie fallback.

Only the verifier constructs VerifiedCookie; it has no Deserialize, Serialize, Debug, Clone or public constructor. Its workspace and exact bearer token can be read by trusted in-process adapters, never logged. Verification errors are fixed non-disclosing codes; key/token/signature/header values never enter diagnostics. This is proof of MAC verification under the configured key, not proof of DB identity, expiry or runtime generation. Runtime must still bind stable distinct databases, current secret/workspace generation and manifest/lifetime admission. Secure naming is not proof of TLS/origin/proxy correctness.

A new application entrypoint takes VerifiedCookie and a trusted runtime Clock (SystemClock in production; deterministic test implementations), not caller user/session IDs, roles, timestamps or an authenticated boolean. Authentication and freshness are admission-time checks, not commit-time validity: a later boundary crossing during company-lock acquisition or callback does not cancel already admitted synchronous work. Under control BEGIN IMMEDIATE, exact session.token lookup resolves session ID and subject; complete current control schema/history and integrity/FKs remain mandatory. Dates must be canonical UTC ISO milliseconds YYYY-MM-DDTHH:MM:SS.sssZ TEXT with valid Gregorian/time fields. Require createdAt<=now<expiresAt, positive lifetime<=the existing12-hour policy and, for Fresh operations, age<the existing10-minute freshness policy. Unknown/malformed dates, future creation, expired/deleted/retokenized sessions or stale freshness refuse before company work. Re-read the trusted clock at admission under the lock; business input cannot set it. No date coercion, session refresh/cache, renewal, cookie issuance or control data writes occur. Session IDs/subjects must be exact nonblank source text; actual current user email/MFA/access/membership and company policy still run under that same lock.

The existing trusted-provider entrypoint and its explicit caller obligations remain for compatibility. Both entrypoints share one transaction implementation, including WAL/DELETE admission and NotCommitted/OutcomeUnknown/Committed cleanup semantics. Cookie workspace must match the selected workspace before callback; unknown session IDs cannot be supplied through this path. Postcommit receipt replay still needs current authorization. Callback transaction-control SQL/sidechannels remain forbidden, not sandboxed. Runtime must map operation to company permission and freshness statically; callers cannot select their own required permission.

Acceptance: independently generated Python HMAC vectors and malformed/duplicate/profile/key-rotation/control-byte cases; actual installed Better Auth issuance and server session authentication compared with native results on synthetic current control stores; exact timestamp/freshness/expiry boundaries and explicit fail-closed differences retained. A real fixed synthetic key/token is allowed only in fixtures, never real secrets/company data. Native execution outside repo cwd and hostile actor/timezone environment remains deterministic for fixed Clock; SystemClock is exercised separately. Under synchronized processes, session token change/deletion is either observed before admission (deny) or blocked until ledger commit; no pre-lock token-to-ID gap or later ID-only substitution may authenticate the old token. Existing control-fence/process and access-policy suites stay green; secret/redaction, format/Clippy, scoped readiness and independent review pass. Full Rust platform completion remains unproven and active.

Explicit source differences: Better Call keeps the first duplicate cookie, leniently accepts some malformed percent/quote spellings and accepts equivalent noncanonical base64 pad bits; this adapter refuses ambiguity or malformed/noncanonical wire. Legacy blank service headers count as absent, whereas this human-only adapter refuses any presented service header. Better Auth getSession permits exact expiry equality (rejects only expiresAt<now); Rentemester HTTP freshness permits exactly600000ms while Better Auth freshSessionMiddleware refuses >=600000ms. Native expiry and Fresh both use strict exclusive deadlines. The installed internalAdapter can issue24-hour dontRememberMe sessions even under expiresIn12h; native refuses lifetimes beyond12h. These are deliberate fail-closed policy differences, not claims of complete parser/session parity. Actual framework evidence uses internalAdapter session issuance and its serializer/getSession; existing actual HTTP login/MFA/reset suites remain separate regression evidence.
