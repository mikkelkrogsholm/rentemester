# Legacy journal hash compatibility

This bounded R03/R09/R10/R11 increment adds `rentemester-rust verify-journal-hashes --company PATH` and a reusable Rust storage function. It verifies the existing journal canonical hash chain over the same private current-schema snapshot as the trial-balance reader. Existing commands and ledgers stay unchanged. Full epic, baseline, schema/writer, audit-log completeness and full verifyAuditChain parity remain outstanding.

Input: one explicit nonempty local company path, exactly one separate --company value, no other flags/default company/actor/retry. Help is successful. Same qualified Unix no-follow capture, 512 MiB source-byte bound, four stable-capture attempts, private recovery/cleanup and v36 history/FK/table checks as the preceding reader apply. Additional hash columns must have expected table metadata. Unsupported platform/history/storage is a typed refusal, never migration or repair.

Read entries by INTEGER id ascending, lines by INTEGER id ascending. Canonical entry IDs and nullable references must be JS-safe integers; journal-line IDs are used only for SQLite ordering, never converted to JS numbers. Required strings must be valid UTF-8; do not trim or normalize stored text. Optional VAT/line text remain explicit null or exact strings, preserving empty strings. Header nullable number fields remain null or finite supported SQLite numeric values. Refuse TEXT/BLOB numeric storage, unsafe INTEGER precision, nonfinite values and negative debit/credit. This is an explicit fail-closed difference from the legacy hash helper's permissive invalid-line-to-zero normalization.

Canonical JSON property order is exactly: id, entry_no, transaction_date, text, source_bank_transaction_id, document_id, currency, amount_foreign, amount_dkk, fx_rate_to_dkk, rule_version, created_by, created_by_program, status, reversal_of_entry_id, lines. Each line is ordinal, account_no, debit_amount, credit_amount, vat_code, text. Ordinal is zero-based position, not the stored line ID. Header FX metadata is serialized from persisted numbers without further rounding. Required current-schema columns cannot be omitted or silently invented.

Line normalization reproduces roundDkk: ECMAScript shortest f64 decimal spelling, decimal half-away-from-zero to integer cents, conversion of that integer to binary64, division by 100, then ECMAScript JSON number spelling. Refuse if that conversion is nonfinite. Number spelling includes 1e+21, 0.000001 and negative zero as 0. This compatibility arithmetic belongs to the legacy persistence adapter; the pure accounting engine retains exact integer cents. Never replace legacy hash bytes with exact-string money or sorted-key/JCS JSON.

String serialization uses JSON.stringify-compatible UTF-8/escapes for valid Unicode; no NFC normalization, slash escaping, case changes or extra whitespace. SHA-256 input is canonical JSON UTF-8 immediately followed by previous stored entry_hash UTF-8, without separator/newline. First predecessor is literal GENESIS. For every row compare stored previous_hash to the preceding stored hash and stored entry_hash to the recomputed hash, then advance using that stored entry_hash, matching legacy traversal. A null first previous_hash is a mismatch, not an implicit GENESIS. Entries with no lines cannot return a successful hash check. This reader neither rewrites historical rows nor introduces a new hash version.

Result is one JSON line, empty stderr: {ok,format:"rentemester-journal-hashes/1",data:{ok,entriesChecked,errors}}. A valid chain (including empty) returns exit 0, ok true and no errors. A checked mismatch/no-lines returns exit 1, ok false and diagnostic strings naming the entry. Ordinary source/schema/decoding failures return {ok:false,code,errors}, exit 1; malformed CLI input uses invalid_input and exit 2 before opening a company. No partial successful result on decode/storage failure. No stored canonical payload or filesystem path is returned in a successful result.

A matching hash chain is not full accounting integrity: omitted tail without an external trusted checkpoint, privileged history rehashing, audit_log completeness, balanced lines, document bytes, semantic reversal validity, invoice/bank evidence, full trigger/view health and hosted company authority are not proven. audit_log has no cryptographic chain in the existing product. Keep this scope explicit in help and result format; do not substitute it for existing full verifyAuditChain.

Acceptance: real synthetic TypeScript posting/reversal paths produce a chain Rust verifies without writes; fixed independently saved canonical byte/hash vectors cover property/line order, null versus empty, Unicode/controls/NUL, FX exponents, large numbers and rounding tails. Altered text/actor/header/line/order/predecessor/hash and missing lines must fail. Wrong amount/order/omitted-field comparison controls fail. Unsafe IDs/nonfinite/malformed types, schema drift, missing/symlink source and usage errors refuse. Source file/sidecar inventories must match before/after success and refusal; real WAL-backed source is exercised. Cargo format/strict Clippy/tests, previous read-only/wire checks and relevant legacy audit tests must pass. Preserve actual revision-bound evidence and review findings separately from GDD structural readiness.
