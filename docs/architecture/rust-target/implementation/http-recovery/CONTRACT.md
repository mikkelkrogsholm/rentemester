# Native HTTP recovery callback and completion

`rentemester-server::recovery_router` adds GET /api/auth/reset-password/{token} and POST /api/auth/reset-password to the existing request route. It accepts three trusted synchronous handlers for existing native request/callback/completion use cases. The existing request-only reset_router remains available. No default handler opens data, accepts a workspace path from HTTP or grants product mutation authority; actual physical/workspace lifetime, legacy writer, enabled provider and connection-retirement admission remain prerequisites. The ignored fixture helper alone opens synthetic controls from private stdin. R41/R42 and full epic acceptance remain incomplete.

Mail callback is navigation, not a POST: it requires one configured canonical Host, permits missing Origin and cross-site Sec-Fetch-Site, and rejects foreign/duplicate Origin if present. It does not require a session or issue one. HEAD is explicitly405 with Allow:GET and never calls the executor or consumes callback rate/capacity; Axum's implicit HEAD behavior is deliberately overridden. The path token must be the canonical24 ASCII alphanumeric bytes; percent-encoded aliases refuse400. Exactly one literal callbackURL query key is required, including an allowed empty value; duplicates, additional keys, over8192-byte query, malformed percent escapes and invalid UTF8 refuse400. Values decode once with form plus handling. RecoveryLinks separately validates the destination against the configured origin. This rejects open redirects independently of request Origin/Host.

Callback invokes the existing admitted read-only reset_request::callback under a blocking permit. Existing strict unique/current token, existing-user, valid timestamp/lifetime and expiry rules decide validity; no cleanup, token consumption or reservation occurs. A valid link returns302 with a validated same-origin Location containing token; invalid/expired/consumed/orphan rows yield the trusted redirect with error=INVALID_TOKEN. Empty callback follows existing /api/auth/error?error=INVALID_TOKEN behavior. The adapter revalidates the handler's returned sensitive URL before placing it in a sensitive HeaderValue. Handler failure, wrong-origin output or panic returns fixed503 RESET_UNCONFIRMED without Location. The URL-bearing response is no-store/no-referrer/nosniff, with no cookie/session or body token JSON.

Completion requires the existing strict POST Origin/Host/fetch/media gates and no query string. Only strict JSON {token,newPassword} is accepted: no duplicate/unknown fields, nulls, alternative body/query token precedence or trailing values. Current retained UI already sends body-token, so source query fallback is intentionally refused. Common body admission enforces8192 bytes and two ordinary-scheduling seconds including chunked/stalled input. Token must be canonical24 alphanumeric bytes. Shared native constants enforce12–128 original UTF16 code units before NFKC/KDF; shorter/longer values return source400 PASSWORD_TOO_SHORT/PASSWORD_TOO_LONG. Existing source messages/code JSON are fixed and no raw password or parser data is returned.

Completion executes password_reset::execute on the owner's admitted connection off the async loop. KDF runs outside the SQLite transaction; the current token is re-resolved under the eventual writer and password/account creation, token/sibling invalidation, session revocation, native auth-state and audit effects commit atomically. Reset possession does not grant workspace access, email verification, MFA or session authority. Only Ok after known commit maps to200 {"status":true}. NotCommitted invalid_credentials maps to source400 {"message":"Invalid token","code":"INVALID_TOKEN"}, including missing/expired/consumed/orphan recovery. Every other operational failure, OutcomeUnknown or JoinError is503 {"message":"Reset outcome could not be confirmed","code":"RESET_UNCONFIRMED"}. There is no Retry-After on these outcomes, success claim, rollback claim, automatic mutation retry or token regeneration. The trusted handler retains detailed stage/connection retirement observations internally; HTTP never exposes them.

All three routes share four non-waiting owned application permits and one bounded4096-entry process-local rate map. Keys contain normalized socket IP and a fixed operation enum, never token/query/password. Request issuance remains3/60 seconds; callback and completion each allow10/60 since the last admitted request. Varying callback token paths cannot bypass a bucket. IPv4-mapped normalization, IPv6 /64, ignored forwarded identities, expiration and atomic counters retain the request-boundary policy. Body admission and queued/running blocking jobs hold permits; cancellation/disconnect retains capacity until actual work ends. HTTP cancellation does not cancel a started mutation. This is not persistent/shared/restart/proxy rate qualification, a global socket/header limit, hard realtime or bounded whole-runtime shutdown.

The retained React reset view treats explicit RESET_UNCONFIRMED, transport loss and malformed acknowledgement as unconfirmed, clears password/token and removes the old form. It offers login and a new recovery request without claiming success, invalidity or rollback, and never resubmits the old bearer. Per-call retry:0 prevents fetch-library retries. Only data.status===true with no error shows the existing success view. Known business refusals keep the existing generic refusal. The existing query-removal behavior still removes the token from navigation history. Focused UI tests cover success, known refusal and three uncertainty modes with no private provider text; app typecheck qualifies the real client signature. No browser/server deployment or whole rendered application parity is implied.

Neither this module nor its response mapper logs bearer, query, email, password or raw provider failures. Parser/HTTP/KDF/dependency copies are not universally zeroized. The injected handler is trusted: concealing a panic from HTTP does not suppress Rust's process-global panic hook or sanitize an arbitrary handler's logging. Existing private-root/TLS/proxy policy, physical writer/lifetime, connection/header/TLS listener, readiness/capabilities/assets, other identity/provider routes and distribution/cutover gates remain binding. No actual user/company adoption, external email, production mutation or deployment is exercised.

Acceptance uses15 focused native server tests, including real mail navigation without Origin, strict query/path decoding, HEAD refusal, fixed token-free rate keys, UTF16 bounds, all completion failure stages/panic and shared permits after cancellation.
