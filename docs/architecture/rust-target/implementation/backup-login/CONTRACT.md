# Native encrypted backup-code login

Extend the existing enrolled native password/pending-MFA transaction with backup-code verification as an alternative second factor. Require the same signed native challenge, trusted workspace/cookie/keyring/clock, canonical admitted control snapshot, current verified email/active access/verified MFA row and current credential/factor/lifecycle context. No password, service or session-cookie fallback and no session before the second factor. This scope is pending-login recovery, not enrollment, viewing/regenerating backup codes or recovery from a lost password.

The installed configured Better Auth profile stores an encrypted JSON array of ten default backup codes; consumed pools contain zero to ten codes. Each code is exactly five ASCII alphanumeric characters, a hyphen and five ASCII alphanumeric characters, case-sensitive with no trimming or normalization. Accept bounded JSON whitespace/escapes, but refuse malformed JSON, wrong shapes/types, duplicate entries, more than ten entries or nondefault code profiles as unsupported stored state. Use the existing injected MFA keyring and authenticated current/historical envelope handling; no environment lookup or key guessing. A malformed encrypted pool is an operational refusal with no spent attempts. A valid empty pool or absent/malformed submitted code is an authentication failure with the existing shared five-attempt challenge and ten-failure/fifteen-minute account lock budgets.

Compare all validated pool entries using fixed-length constant-time comparisons, without early match return. On a match, remove exactly that unique entry, serialize remaining codes in order and encrypt with a fresh nonce/current key. Owned parsed code buffers and serialized plaintext zeroize; wrappers do not expose Debug/Clone/Serde. Library parse internals, caller inputs and whole-operation constant-time execution are outside that claim. No plaintext code, pool, envelope, cookie or credential-derived fingerprint appears in persisted diagnostics or evidence.

Under one control BEGIN IMMEDIATE, update the exact factor row with an old-ciphertext compare-and-set, reset account failure state, consume all pending challenge records, create the existing fresh twelve-hour session and append accepted recovery telemetry plus the immutable session-created trigger. Wrong codes and locked attempts use the distinct source endpoint two-factor-verify-backup-code in audit. Backup success does not create, reset or advance the TOTP replay record. Concurrent uses of the same code, even through different pending challenges, cannot create two sessions. Different still-current codes remain usable through other valid pending challenges; the pool is read from the locked current factor, not captured plaintext at issuance.
