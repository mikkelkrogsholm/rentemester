# Native reset-request HTTP boundary

The `rentemester-server` library exposes `reset_router(origin, CookieProfile, executor)`: exactly `POST /api/auth/request-password-reset`. It is the first concrete Rust HTTP identity route, exercised on real loopback sockets. It is not a full R41/R42 server, a product writer grant or a deployable server executable. A trusted runtime supplies the executor and retains actual physical-handle/workspace lifetime admission, configured enabled mail, connection retirement and existing writer/migration gates. No default executor opens any workspace; HTTP cannot select a workspace, database, signer, subject or provider. Only the ignored synthetic test helper opens fixture paths supplied on its private stdin.

Construction validates one explicit canonical origin through existing RecoveryLinks policy. Secure profile requires HTTPS; development HTTP permits only configured localhost/loopback. Request Origin and Host must each occur once and exactly equal the configured canonical origin/authority. Missing/null/duplicate/foreign Origin is refused even without cookies. Forwarded host/proto/IP headers never establish authority or a rate identity. If present, Sec-Fetch-Site must be same-origin, same-site or none. This same-origin route has no cross-origin CORS grant. Trusted redirects are separately validated using RecoveryLinks against that one configured origin; relative valid destinations remain allowed. It does not derive deployment configuration from request headers.

Only application/json with optional charset=utf-8 parameters is accepted, case-insensitively; duplicate Content-Type and every Content-Encoding are refused. Query parameters on this route are refused. Strict JSON has required string email and optional string redirectTo; explicit null, duplicate fields, unknown fields, trailing JSON and invalid UTF8 are refused. Email uses the existing practical ASCII credential lookup grammar and lowercasing without trimming. Redirect validation precedes executor work. The body cap is8192 bytes even without Content-Length/chunked, with a two-second ordinary-scheduling body-read deadline. Oversized/unreadable bodies return413, body deadline408, bad JSON/email/redirect400, media/encoding415 and origin/host/fetch/query/peer admission403. Responses contain only fixed request_refused codes, never parser or provider details.

Rate admission uses only Axum ConnectInfo populated from the actual accepted SocketAddr, never raw client headers. Missing peer refuses. IPv4-mapped IPv6 normalizes to IPv4; native IPv6 shares its /64 prefix. An atomic mutex protects at most4096 in-memory IP buckets. Each bucket admits at most3 requests until60 seconds after the last admitted request; admitted calls update lastRequest, refused calls do not. Expired buckets are removed before admission. Full map or rate denial returns429 with fixed Retry-After60, independent of email/existence. Invalid JSON also consumes rate admission. Origin/media admission happens first. This process-local bounded implementation deliberately does not claim source database persistence, restart resistance, multi-process limits or trusted-proxy client identity. A proxy currently shares its socket peer bucket. Those are production/release admission gates, not an excuse to trust arbitrary forwarded headers.

At most4 admitted bodies/jobs share one non-waiting owned semaphore. Full capacity returns503 before body parsing/executor work; there is no unbounded application job queue. Body validation holds the permit. After validation, spawn_blocking owns it through the entire trusted executor, including its native transaction and postcommit mail. Dropping the HTTP future/JoinHandle or disconnecting does not free capacity while blocking work continues, cancel a started mutation, regenerate a token or establish rollback. Work may wait within Tokio's blocking pool; global pool/sockets/header-read admission and hard shutdown remain unqualified. No request timeout wraps a potentially committed operation and reports it as canceled.

For every admitted executor outcome, including known/unknown account, rollback/unknown commit, postcommit delivery uncertainty or JoinError, public output is exactly200 application/json with {"status":true,"message":"If this email exists in our system, check your email for the reset link"}. Cache-Control:no-store, Referrer-Policy:no-referrer and X-Content-Type-Options:nosniff are fixed; no cookie or session is issued. Status/body/header mapping cannot expose the internal Failure stage or recipient. This is acknowledgement of the attempt, not delivery success, constant-time/constant-I/O privacy or guaranteed execution. The trusted executor must retain internal connection-reuse/commit observations before returning them. Its own logging/panic policy must exclude sensitive data; this library installs no logger/panic hook and cannot sanitize a malicious or panicking injected executor's process-wide hook output. Static router404/405 fallbacks are Axum defaults, not the admitted JSON response contract.

Native input/body copies owned here use Zeroizing where practical; JSON/parser/HTTP buffers and all dependency copies are not universally zeroized. No raw body/email/redirect/token/provider diagnostics are logged by this module. No external mail, actual user/company adoption or production mutation is exercised. Callback/completion/login/MFA/session/verification/service routes, capability/health/readiness, SPA/binary assets, hosted TLS/connection admission, deployment/shutdown, persistent/global throttling and the entire cutover remain required later work.

Acceptance combines real socket tests (ACK/rate spoofing, host/origin/media/JSON refusal, content-length/chunked limit, stalled body deadline, route limits), atomic concurrent rate/capacity/window tests and cancellation-held blocking permits. A separate20-case process suite starts the Rust router with a synthetic executor that calls the real native reset_request::execute under WAL and DELETE: known/unknown/mail-failure ACKs match an actual installed BetterAuth handler; link/audit effects, rollback and unchanged users are inspected; mail asserts independent connection visibility and no SQLite writer is held. Hostile Origin has no native effect. Source special rate rule is3/60 with lastRequest updates and IPv6 /64 normalization. Source cookie-free Origin permissiveness, loose media matching and unknown-field stripping are deliberately tightened. Source mail errors are swallowed after persistence; native preserves explicit internal commit/delivery uncertainty and conceals it here.

Primary references are the installed pinned source `better-auth/dist/api/routes/password.mjs`, `api/rate-limiter/index.mjs`, `api/middlewares/origin-check.mjs`, `better-call/dist/utils.mjs`, local src/server/better-auth.ts, existing reset-request/recovery contracts, and the locked [Axum serve](https://docs.rs/axum/0.8.9/axum/fn.serve.html), [bounded body reader](https://docs.rs/axum/0.8.9/axum/body/fn.to_bytes.html) and [Tokio spawn_blocking](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html) APIs. Scoped GDD structural readiness, regression and independent review bind this finite boundary; no narrow result closes the full issues.
