# Native authenticated password change, HTTP and retained account UI

Implement own authenticated password change through a caller-admitted native control connection and POST `/api/auth/change-password`. Authority requires a runtime-bound signed current-session proof and the current password, never a body user/email/provider/workspace selector. Runtime supplies CookieVerifier, trusted Clock and bounded audit version; no MFA keyring is needed for this use case. The storage primitive is not a standalone authentication grant: its caller must verify the current KDF and recheck the exact captured credential/session under this same writer. No default data opener, physical/lifetime grant, server-only setPassword method or service principal authority is added. The serving owner still must retain physical/control/workspace lifetime admission, retire unusable handles and drain/exclusively route independently running legacy writers before real enablement.

Validate original new-password length12..128 UTF-16 units before the shared NFKC password KDF; current-password input remains bounded4096 UTF-8 bytes. Prepare the replacement hash outside any SQLite transaction. Capture the canonical existing local credential by the verified session token in a read snapshot, end that read, verify current password without a writer lock, then recheck that exact credential/access snapshot under BEGIN IMMEDIATE. Sample trusted time for final admission; resolve the same current token/subject/session ID with freshness younger than ten minutes and maximum twelve-hour lifetime, and require verified email, active member/owner access and one enabled/strict verified MFA factor. Credential/session/access changes during unlocked work cannot authorize the final mutation. New hashing occurs before credential capture/current-password verification, with bounded endpoint worker/rate protection; neither KDF holds the writer. Unsupported/missing local credential or wrong current password refuses, without creating an account or session.

Under the same held writer, CAS-update only the unique canonical existing local credential's password/updatedAt, with a fresh canonical source-compatible hash. Refuse an unchanged hash at this trusted persistence primitive. Invalidate all outstanding own source reset-password links so an older link cannot undo the authenticated change, preserving other subjects and verification namespaces. `revokeOtherSessions=false` or omitted preserves every session row, including its age/expiry/metadata. True atomically deletes all own sessions, including current and expired, then inserts exactly one fresh native12h session; no foreign session is touched. Cookie issuance is prepared before commit. These operations do not modify user flags, MFA factor/backup pool, failure/lock state or existing TOTP replay rows. Existing credential_updated/session_deleted/session_created triggers provide lifecycle evidence; credential history invalidates earlier native pending-login contexts even when sessions are retained.

Append one accepted workspace_audit event `password_changed`, entity_type `native_password_change_v1`, entity_id canonical JSON [subject,originalSessionId,auditKeyVersion,newSessionIdOrNull,deletedOwnSessions,invalidatedResetLinks], actor user:<subject> and created_at from the sampled clock. No password/hash/bearer enters that event. There is no change-password endpoint in the current auth-telemetry schema; no unsupported telemetry label or migration is introduced. Prepare and bound the allowlisted native user JSON to65536 bytes under the writer after applying all effects and validating the resulting user/session metadata, before commit. Late metadata/serialization/SQL failures roll back credential, links, session effects, triggers and audit together, releasing no user/cookie receipt. Process death before commit also rolls back the complete transaction. Every commit error is OutcomeUnknown, retires the connection and releases no user/cookie/success; it does not prove unchanged database state or justify automatic replay.

The HTTP handler is explicitly optional and owns the canonical path; without it404 returns with no legacy forwarding. Require configured Host/Origin, same-origin-compatible fetch-site, JSON without content encoding, no query and strict current-session cookie provenance. Reject mixed Authorization/service credentials, pending proof, duplicate/bare named credentials and malformed Cookie headers. Body must be a JSON object containing currentPassword/newPassword strings and optional boolean revokeOtherSessions; absent means false, but null/string/array/duplicate/unknown fields refuse. Shared body/capacity bounds remain8192 bytes/2seconds/four blocking workers. The operation has its own direct-peer3/10second KDF bucket in the shared identity rate map, unaffected by forwarded headers or rotation-flag changes. HEAD405 never dispatches or charges its POST rate. Common429 conservatively uses Retry-After60; process-local rates are not a distributed/per-account/proxy admission claim.

Only known commit emits200 `{"status":true,"token":null,"user":{...allowlisted native user...}}`. Always keep bearer tokens out of JSON. True alone clears the four configured native auth cookies and sets the prepared new browser-session cookie; false/omitted sets no cookie. The result uses no-store/no-referrer/nosniff JSON. Not-committed invalid credentials maps to401 INVALID_CREDENTIALS; new-password policy maps to400 PASSWORD_TOO_SHORT/PASSWORD_TOO_LONG; operational/metadata/schema/crypto/unknown/panic/bad handler receipt maps to503 AUTH_UNCONFIRMED, with no user or cookies. No implicit retry, legacy fallback or session grant after uncertainty is added. Transport loss after a known server commit remains a client uncertainty, even though native transaction success was known internally.

Installed Better Auth's source endpoint hashes new before verifying old, updates the account and optionally deletes all own sessions then creates a new one. Its false/omitted branch preserves sessions. Source performs separate adapter writes and returns {token,user}, with a bearer when rotating and no status field. Native changes deliberately add Fresh/MFA/access/credential fencing, atomicity/audit, own reset-link invalidation, bounded user projection and token-free JSON; these corrections are explicit, not byte-compatible source response/error claims. Actual source crypto reads native hashes, the source session reader accepts the rotated native cookie, and a later actual source HTTP password change is admitted by the native current-credential fence.

The retained account menu continues to request revokeOtherSessions:true, warns that other devices must log in, validates new-password confirmation and sends explicit fetchOptions.retry0. Before showing success it requires an own-user receipt and rejects any present status that is not exactly true, accepting the source's valid user-only acknowledgement as well as native status:true. Empty/null/wrong-user/false ACK, service refusal or transport failure never claims success or automatically refreshes/replays; entered password fields clear on completion/failure. Guidance explicitly says the change could not be confirmed and suggests manually trying the new then previous password when logging in. A positive receipt alone triggers normal session refresh and confirmation. Browser/JavaScript memory erasure and a deployed browser-native journey are not claimed by the mocked UI tests.

Acceptance uses actual canonical synthetic WAL/DELETE controls, installed source crypto and source-signed cookies, both explicit rotation flags plus omitted HTTP flag, exact own/foreign session and reset-link facts, lifecycle/audit counts and preserved user/factor/replay state. Each native branch seeds replay through a real TOTP acceptance and asserts its exact row unchanged. Cover prior pending-context invalidation, old/new login, original UTF-16/Unicode policy, unlocked credential/session/access changes at both KDF boundaries, concurrent change/writer contention, late SQL/bad-user-result rollback, killed-before-commit rollback and real DELETE unknown commit in both branches. HTTP tests add strict body/credential/origin/schema bounds, HEAD/rate/no-fallback and commit-aware cookie/user mapping. Socket units cover invalid/unknown/panic/bad receipt/absent rotation and malformed objects. UI tests qualify native/source positive receipts, malformed/unknown refusal and no replay; installed-client probes record encoding without secret values. No real data, external mail, live legacy closure, complete identity/provider/service/API-key/trusted-device, /api/me context, actual physical/lifetime/restore admission, CLI/MCP/React/GPUI distribution/cutover or full epic completion is qualified.
