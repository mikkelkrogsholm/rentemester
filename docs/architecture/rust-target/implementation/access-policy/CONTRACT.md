# Shared Rust access policy

This R13 increment creates `rentemester-application::access` for the common workspace/company route decision. It consumes already authenticated, current control facts supplied by an in-process trusted adapter and returns only `Decision { allowed }`. It performs no I/O, has no ambient actor fallback, issues no authorization capability and is not exposed through a product transport. The complete epic remains the goal.

`Permission`, `WorkspaceRole` and `CompanyRole` use the exact existing 23 permission strings and two/four role strings. Unknown vocabulary refuses deserialization. `role_allows` is only a presentation/policy-table query. Workspace ownership grants no implicit company access. Company owner grants every explicitly enumerated company permission, never future unknown permissions. Bookkeeper/reviewer/reader retain the exact current matrix, including knowledge/ownership exceptions.

`authorize` receives an explicit workspace key and optional company slug, an optional identity observation, optional workspace access and optional company observation. These facts do NOT implement `Deserialize`. They are not authentication claims from a JSON request. An identity must have nonempty exact workspace/subject keys, match the requested workspace and be authenticated. Humans require both verified email and enabled MFA; service identities require a registered service account AND verified live credential. A human may not use the service-account bypass. Local actor policy/authentication requires a separate adapter; an actor string or held workspace lease is insufficient.

Public read and invitation claim allow anonymous access as in the current policy; claiming still requires its separate invitation validation. A generic route allow is not approval for every operation: service credential administration still requires a hosted human session even when a service role allows `workspace.manage`. Every private permission requires active workspace access matching both exact workspace and subject. Workspace permissions use only the workspace role and ignore company data. Company permissions additionally require an exact ASCII slug (`[a-z0-9][a-z0-9-]*`), registered nonarchived company in the requested workspace and active membership matching workspace, subject and company. Cross-workspace, cross-subject and cross-company observations refuse. No trimming, case folding, environment lookup, path inference or ID creation occurs; an adapter must resolve source values before calling.

No denial detail distinguishes missing companies, identities, security readiness, membership or insufficient role. Repeated evaluation of immutable observations is deterministic and has no effects. A prior allowed result never authorizes later work: integration MUST load/reauthorize under the future control/ledger revocation fence and reauthorize before returning protected idempotency receipts. This increment does not establish that fence, session verification, credential lifecycle, last-owner mutation guards, source adapters, stable persisted IDs, R04 identity-provider selection, or full R13 acceptance.

Acceptance: independent fixed Python policy matrix (all roles/permissions/security states plus explicit binding counterexamples), native Rust output versus those fixed expectations, actual unchanged TypeScript role policy and source-backed `authorizeWorkspaceRoute` on synthetic current control stores for corresponding cases, strict unknown vocabulary rejection, immutable inputs and repeated calls. Retain explicit differences: Rust requires a verified credential/session observation while legacy core assumes an upstream authenticated caller and accepts any registered service-account row; do not pass caller-controlled facts to product APIs. Domain/application dependency guards must reject I/O/storage/transport dependencies. Scoped GDD readiness precedes implementation; format, Clippy, native tests, corpus parity and existing regression checks must pass. Only synthetic files may be written.
