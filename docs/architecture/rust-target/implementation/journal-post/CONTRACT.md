# Native manual journal posting

Implement a real manual post through the existing authenticated human control→company fence on admitted connections. Storage writes actual canonical journal header/ordered lines, fiscal sequence, chained hash, retention, journal_post audit, bank-exception resolution and optional durable receipt in one company transaction. Canonical synthetic current-v36 ledgers qualify this use case. Original-path/lifetime/restore admission, service company quota/fence, product HTTP/CLI/MCP endpoints and outer actor-policy/backup/confirmation adapters remain required before deployment; reversal remains a separate append-only workflow. No real company data, mail or live migration is used.

Business input is the existing strict typed ManualJournal with exact two-decimal money, six-decimal FX, canonical date/currency/identifiers and expected compiled rule version. Runtime derives actor from the CURRENT authenticated subject under the held control writer and uses fixed rentemester-rust program; caller program/actor authority is refused. Registered active company and CompanyLedgerPost permission are rechecked by the existing fence before any protected result/replay. The application reads a trusted Clock under the company transaction, converts UTC milliseconds to Europe/Copenhagen using compiled IANA data and adds runtime-configured maximum-future-days (default45), never request latestAllowedDate or host TZ. Public runtime inputs cannot override time. Chrono/Chrono-TZ are added for this required date conversion, with locked versions; APIs documented at https://docs.rs/chrono/0.4.45/chrono/struct.DateTime.html and https://docs.rs/chrono-tz/0.10.4/chrono_tz/ .

Storage requires main Write state, current checksummed history and exact canonical physical schema/integrity, without migration/capture/path opens. Reuse the existing compiled manual validator and source fact collector against the actual borrowed connection: accounts/roles, document register/credit-note prior posts, bank links, covering period audit lifecycle. Period locks/reopened/reported states, future horizon, balanced nonnegative one-sided lines, explicit VAT, FX and evidence checks stay active. Actual FKs/credit-note/bank-source uniqueness and append-only triggers stay active; missing optional balance-only document or already-direct bank source must not bypass SQL constraints. Validation refusal preserves source appliedRules/error messages without effects; every SQL or post-effect refusal requires caller rollback.

Read source company settings from first id row, with no-row company-1/January/end-year defaults, normalized optional DK+8digit CVR and source fiscal strategy/defaults. Allocate journal_entry companyKey:fiscalLabel sequence using the exact fiscal-prefix all-digit variable-width maximum suffix as floor, then minimum5digit suffix. IDs for header/lines/audit are checked positive JavaScript-safe MAX+1, refusing exhausted or poisoned streams rather than SQLite random fallback. Existing generated source IDs beyond this safe range and malformed metadata require explicit refusal. All new numeric storage must round-trip exact cents/micro-rate through legacy binary64 and SQLite NUMERIC; reject precision loss or nonfinite/unsafe scaled values atomically rather than silently change accounting values. Non-DKK source binary64 FX multiplication must agree with exact multiplication: ambiguous cases (for example3.00×1.005000 yielding source3.01 versus exact3.02) refuse as unsupported_legacy_number in this legacy-storage adapter. The advisory exact engine remains unchanged. Source zero-document truthiness for income/expense is preserved at this adapter boundary.

Preserve entry/line text, nullable versus empty line text and explicit ECMAScript-trimmed VAT code (no chart default). Header currency is canonical, all stored journal lines use DKK. Optional header amounts/rate are source-rounded legacy values; header status posted, reversal reference NULL, locked default1, fiscal retention deadline exact. Hash uses source declaration order, safe row identity and line ordinals, JS numeric JSON and SHA256(JSON||latest stored hash), GENESIS only when empty. Reuse the existing hash encoder and verify newly stored canonical data/hash/retention before commit. This does not invent a mandatory full prior audit/evidence-byte verification gate absent from source core.

Insert exact journal_post/journal_entry audit with source message/actor attribution. Resolve only open UNMATCHED_BANK_TRANSACTION exceptions attached to a positive source-bank ID, with exact source note/actor and SQLite timestamps; source helper's nonpositive-ID no-op is retained. Any companion/receipt error aborts all header/line/sequence/audit/exception effects. Process death before commit leaves none; known company commit survives control-cleanup failure, whereas commit uncertainty withholds successful posting/receipt and retires affected handle(s), with no automatic retry.

Optional client idempotency uses journal_post plus current stable human subject and the existing durable receipt primitive inside the same transaction; authorization precedes replay. Fingerprint is the versioned native typed business request (including compiled expected version, excluding key/confirm and runtime actor/time). Typed money strings and explicit optional fields are a native protocol contract: legacy adapters must preserve their original validated fingerprint when eventually ported; this use case does not claim arbitrary prior legacy transport receipts have the same payload shape. Same native key/payload returns stored entry result without new journal companions; changed request conflicts, pruned outcome refuses and immutable key remains reserved. Business rejection returns no success receipt and retains original errors after rollback.

Acceptance compares actual TypeScript manual posting against native real canonical ledgers: exact header/lines/hash/no/retention/audit/exception effects, parsed outcome and successful source audit-chain verification where applicable. Cover DKK/FX/VAT/document/bank/Unicode/null/empty/fiscal strategy and wide suffix, preserved native precision/identity corrections, actual FK/index refusals, period reopen/report, source validation errors and rule mismatch. Fault SQL after each companion, real WAL/DELETE concurrent posters, killed before/after commit, idempotent actual posts, current revoked authorization, trusted Copenhagen DST/midnight boundary and real DELETE commit uncertainty must be evidenced. Full reversal and all R14/epic requirements remain open until their own verified acceptance.
