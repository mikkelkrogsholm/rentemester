# Native owner service credential lifecycle

Deliver owner-only native list/create/rotate/revoke/recover use cases and the five existing /api/workspace/service-principals HTTP paths. Trusted owner retains physical/control/workspace lifetime and must drain independently running legacy/provider workers before enabling any lifecycle/recovery executor. A recovering lease expiring is not evidence that an old provider worker has stopped; a SQLite writer alone cannot fence its later external provider-create. This internal admitted-connection implementation does not establish real drain, product opener, deployment, company/dispatch authority or full identity/platform completion.

Resolve runtime-bound human cookie under canonical control BEGIN IMMEDIATE. Require verified email, enabled strict verified MFA and active workspace_owner, not service credentials or member role. List uses Current12h session policy and rolls back without data/audit/session refresh. All mutations/recovery use Fresh younger than10minutes; actor is user:<current subject>, never request metadata. Bound user/actor/identifiers and inputs; strict explicit confirm:true is HTTP consent, not authentication. operationId input normalizes trimmed UUID version1..8/variant89ab to lowercase, optional new mutations generate UUID4. Recover requires caller-known operationId. Future clients should preassign operationId before sending; an autogenerated id in a lost response cannot be recovered by guessing/retry. No automatic mutation replay.

New create/rotate/revoke effects are one native control transaction: pending and completed operation events, exact source-compatible API-key row, registry/user when creating, precise old key disable and service events. New principals follow source service_<UUIDhex> stable id and @service.invalid nonhuman flags0, with no password/session/access/membership creation. New keys are rms_ plus64 uniformly random ASCII letters, SHA256 UTF8/base64url unpadded, prefix/start/name marker and source default600/60000 rate, remaining/refill NULL. Default expiry90days; internal/HTTP optional expiresInSeconds permits1..365days in seconds. Random UUID4/key generation uses OS entropy; no caller secret/hash/id/actor authority. New rotation retains subject, disables exactly target owner/config-bound key and creates one replacement even when old key already disabled. Revoke disables exactly the bound key, including NULL enabled, and records revocation. Missing/wrong-owner/wrong-config direct targets refuse with no writes. Never reactivate or delete old keys.

Secrets are returned once after a known commit only, in bounded prepared receipt {ok:true,operationId,serviceAccountId,credentialId,secret}, create201/rotate200. Revoke returns {ok:true,operationId,revoked:true}. Same operationId is never reused, including completed/failed/recovered; repeat cannot reissue or redisclose. Late schema/SQL/serialization failure and process death before commit roll back all rows/events/flags. Every commit error retires handle and returns OutcomeUnknown with no receipt or secret; no unchanged-state claim or implicit replay. Runtime key material and prepared secret receipt use zeroizing wrappers and no Debug/Clone/Serialize exposure, but secure erasure of SQLite/process/HTTP/browser memory is not claimed.

Preserve source inventory shape and ordering by registry created_at,user_id and enabled count including expired/NULL-enabled rows (it is not a live-authentication count). Add bounded owner-only credentials:[{credentialId,enabled,expiresAt}] per principal, with enabled nullable to distinguish legacy NULL refused by native verifier. No rawkey/hash/provider marker/metadata/user email is disclosed. This extension allows deliberate cleanup of inaccessible keys after a lost response. Maximum1000 principals/1000 total credentials/1MiB JSON; malformed names/flags/dates or overflow refuses the whole inventory, never partial output. Source UTC registry/event timestamps YYYY-MM-DD HH:MM:SS and canonical ISO-millisecond UTC are parsed strictly; output retains stored inventory createdAt.

Recovery validates the complete selected operation stream in numeric ID order: initial pending; stable operation type/subject/marker/old credential; valid pending→completed/failed/recovering, failed→recovering or recovered, recovering→recovering/completed/failed transitions; terminal states never reopen. Require canonical bounded UUID/marker/actor and strict source UTC/ISO nonfuture timestamps; max1000 history rows. Validate status-specific credential/replacement/claim fields rather than trusting permissive SQLite CHECK NULL behavior. Marker reuse across distinct operationIds refuses before cleanup. Current registered subject is required. Both service event streams must have strictly positive IDs and no existing MAX_ROWID poison; inserts use explicit checked MAX+1 ids, so a multiappend at MAX−1 fails and rolls back instead of SQLite random fallback.

Terminal completed returns status completed,recovered:false; terminal recovered returns recovered,true. Native adds nonsecret serviceAccountId/credentialId/replacementCredentialId readback, never secret; a caller with a lost completed secret can explicitly revoke its replacement with a new operationId. A fresh recovering row (now-created_at<30000ms) returns recovering,false unchanged. At exactly30000ms it is expired. For pending/failed/expired recovering, the held native transaction replaces the source external provider saga: create/rotate disables only own/config/name-marker replacement keys, appends failed (unless already failed) then recovered, never reactivates old key; revoke disables exact bound target if present, appends revocation when found and completed. A deleted revoke target is already absent and completion records no fabricated key event; an existing foreign/config-mismatched target refuses. No persisted recovering claim is necessary because native cleanup and terminal rows commit together, conditional on the owner's real legacy drain. Source transient failed/recovering states are retained truthfully when refusal/unknown prevents native completion.

HTTP optional native handler owns canonical paths with404/no legacy fallback. GET list rejects query/body/encoding, HEAD405 no dispatch/rate. Mutating JSON object only with exact operation fields, required confirm:true, optional nonnull UUID operationId and optional integer expiry for create/rotate; rejects arrays/duplicates/unknown/subject/actor/secret fields. Current signed-cookie provenance, configured Host/Origin/fetch, no service/Authorization, body8192/2seconds and four-worker gates apply; list optional Origin, mutation exact Origin. Shared lifecycle direct-peer10/min bucket across operations, unaffected by forwarded headers/operationId/targets. Known commit/read success alone emits bounded receipt, no Set-Cookie, no-store/no-referrer/nosniff; invalid credentials401, invalid input400, reused operation409, operational/malformed/unknown/panic503 with no partial receipt. No retries or plaintext logging; HTTP known-success issuance necessarily contains the new secret.

Acceptance uses canonical synthetic WAL/DELETE, real source signed owner cookies and installed provider crypto/verification/rotation interoperability. Qualify no implicit access, precise registry/key/event effects, one-time secret/operation reuse and targeted lost-response cleanup, inventory count/ordering/extensions, Fresh/member/unverified/revoked/mixed authority, strict wire input, concurrent operationId and rotations/revocations, actual writer exclusion/busy, late failure/death rollback and DELETE commit unknown without secret. Rehearse source crash states before/after provider-create and old-disable plus failed compensation; strict historical timestamps/30s boundary, malformed transitions/stable facts/marker ambiguity and MAX/MAX−1 multiappend guards. Source-compatible core lifecycle behavior and explicit atomic/readback extensions do not qualify the full deployed management UI, service company/dispatch fence, legacy drain, CLI/MCP/GPUI/distribution/cutover or close entire epic issues.
