# Native reset request, mail handoff and callback

`reset_request::execute` issues a source-compatible recovery link and hands it to a trusted injected mail port only after a known database commit. `reset_request::callback` previews the allowed redirect without consuming a token. Together with existing native reset completion this covers the internal request/link/preview/completion sequence. Public HTTP acknowledgement/CSRF/rate/bounded-blocking dispatch, a concrete Rust HTTP mail adapter, durable delivery/outbox, actual physical control/workspace lifetime admission and deployment remain pending. No production mail is sent by this increment.

The runtime injects a CookieVerifier solely for the existing domain-separated HMAC audit identity, a Clock, RecoveryLinks configuration and JavaScript-safe audit-key version. No signer/session proof grants recovery authority. A ResetSender is a real external boundary: enabled() must reflect already validated transport configuration, and send() accepts only a private-field sensitive ResetMessage with recipient/token/action URL accessors. Its failure is opaque DeliveryUnconfirmed, never raw provider errors. DisabledResetSender refuses by default. Trusted adapters must enforce finite network deadlines, bounded same-message retries and no secret logging. Request issuance never retries by manufacturing another token. Unit output contains no bearer or account-existence field.

Preflight rejects an unready handle first. A disabled sender refuses before identity lookup for both known and unknown emails. Input uses the existing bounded ASCII practical-email grammar and lowercase-without-trimming correction. Redirect and injected configuration are validated before durable effects. A fresh source-format 24-character alphanumeric bearer uses unbiased rejection sampling from OS bytes; generation has a finite entropy-attempt bound and secrets are zeroized. A separate OS-random row ID is generated. Neither subject nor token identity is request-injected. A valid-looking but absent email still generates the unused bearer and follows the writer/audit path; no constant-time or constant-I/O claim is made.

RecoveryLinks uses pinned url 2.5.8 and real parsed-origin equality, never string-prefix matching or a request-derived Host. Config accepts 1–32 explicit HTTP(S) origin entries without path/query/fragment/nonempty credentials/wildcard hosts. Base origin must occur in the explicit list. Secure mode requires HTTPS; Development permits HTTP only for localhost, 127.0.0.1 or ::1. Root-relative destinations follow the source's restricted ASCII path/query grammar, reject authority/backslash and case-insensitive encoded initial slash/backslash, and resolve against the injected base. Absolute destinations must have an allowed parsed origin and no nonempty credentials/backslashes/controls. Relative fragments are rejected; allowed absolute fragments and query values are preserved. All raw URL inputs are bounded to 4096 bytes.

The exact message URL is <origin>/api/auth/reset-password/<token>?callbackURL=<JavaScript encodeURIComponent of the original optional redirect>. Omitted/empty redirect produces callbackURL=. Component escaping preserves JavaScript's unescaped !~*'() and uses %20 for spaces, not form-style +. Only the persisted matched user's exact canonical email receives the message. The use case acquires BEGIN IMMEDIATE, admits current canonical schema/history, samples the Clock once and resolves an existing user by canonical exact email. No password, credential, emailVerified, MFA or workspace-access condition excludes recovery, and none of those states is changed. Known email inserts one unique-checked reset-password:<token> row containing subject and canonical createdAt=updatedAt=now, expiresAt=now+one hour. Accepted issuance clocks range from 0 through 253402297199999. Unknown email inserts no reset row and sends nothing; unrelated expired verification rows are never globally cleaned up. Older links survive a request and are invalidated by the already-specified successful native completion.

Both known and unknown paths commit a native_reset_request_v1 workspace_audit/password_reset_requested event, actor system:auth-recovery, whose JSON tuple is HMAC identity, audit-key version and optional subject. The HMAC exactly matches rentemester-auth-audit-v1 plus NUL and the canonical email with the configured secret's string bytes. Canonical request-password-reset telemetry records attempted, optional subject, HMAC/version and the same trusted timestamp; attempted never claims mail delivery. No audit contains raw email, bearer, URL, password, credential hash or transport error. User/account/factor/access/session/lifecycle state is preserved by request issuance.

All issuance/audit effects commit together before the port is called, with no SQLite transaction or writer held during mail. A known commit may be followed by another writer consuming/revoking the link before mail; a successful send does not reserve or reauthorize it. After confirmed rollback, failure is NotCommitted and the port has not run. Any commit error is OutcomeUnknown, retires the connection and never calls mail. A mail error after known commit is a distinct internal Committed/auth_delivery_unconfirmed failure: the reset row and audit exist and may remain usable. Timeout/failure cannot prove that no email was delivered. Do not return NotCommitted, delete a possibly delivered token or automatically reissue/replay an uncertain request. Unit success means the known recipient's port confirmed the handoff, or an unknown email was generically acknowledged, not guaranteed end-user delivery. The future public mapper must conceal committed delivery/existence differences and keep the same acknowledgement for known/unknown addresses; exposing these internal states directly would enumerate accounts.

Callback runs one admitted stable deferred read snapshot with one trusted Clock sample and no writes. It reuses completion's exact token grammar/current unique-row/existing-user/canonical-time/one-hour-lifetime/strict-expiry rules. Missing or expired tokens yield INVALID_TOKEN redirects; duplicate/malformed control records refuse opaquely. The same token can be previewed repeatedly without consumption or general cleanup. Valid preview is not a reservation, authenticated session or promise that subsequent completion succeeds. Final completion always resolves under its own writer.

Callback revalidates the destination. A valid row and nonempty allowed callback set its token query parameter; an absent/expired row sets error=INVALID_TOKEN. Query replacement follows URLSearchParams.set, preserving the first matching parameter's position and removing duplicate occurrences, while retaining unrelated parameters and an absolute fragment. Missing/empty callback uses <origin>/api/auth/error?error=INVALID_TOKEN. The sensitive URL is returned only after the read transaction has ended successfully. Caller owns transport/input buffers; bearer and final message/redirect URL wrappers have no Debug/Clone/Serde exposure and zeroize their owned strings. Parser intermediates are not claimed universally zeroized.

Installed Better Auth 1.7.1 request normalizes only lowercase, emits the same normal acknowledgement for unknown email, retains sibling links and constructs the same URL. Its runInBackgroundOrAwait catches sender rejection, so a disabled/failing sender can still leave a persisted link and appear successful. Native documents and reports internal committed delivery uncertainty instead of claiming a rollback or silent delivery. Native also refuses insecure/nonexplicit URL configuration and malformed/duplicate/expired-at-equality preview records, and avoids source's unrelated verification cleanup. These are explicit source corrections. Actual HTTP request-origin/CSRF admission is distinct from validating a redirect and is not implemented here.

Acceptance uses synthetic current control fixtures and separate WAL/DELETE processes, real installed source callback and reset completion on native-issued links, source mail-link encoding and observed swallowed sender rejection, trusted-origin/Unicode/encoding/configuration cases, HMAC audit parity, unknown-email/no-cleanup preservation, disabled/unconfirmed ports, no-lock post-commit handoff, contention, late rollback and real commit-busy with no mail. Existing MFA/reset/session regression, full Rust checks, runtime typecheck/lint, actual scoped GDD structural readiness and read-only review bind evidence to final source hashes. No real user/company migration, external mail or production operation occurs.

URL dependency reference: https://docs.rs/url/2.5.8/url/struct.Url.html (parsed origin, join and query operations); the Cargo lock records the concrete transitive dependency graph. This does not qualify whole-platform supply-chain/distribution acceptance.
