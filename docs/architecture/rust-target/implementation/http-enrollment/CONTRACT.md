# Native password-bound HTTP MFA enrollment

This R04/R41/R42 slice completes the native pre-session enrollment ceremony through two explicit HTTP routes and a retained React path. AuthHandlers optionally supplies EnrollmentHandlers; absent handlers leave both routes404. Registered enrollment and existing identity/recovery routes use the same configured cookie verifier, four owned blocking permits and4096-entry socket-IP/fixed-operation rate map. Enrollment begin and confirm each allow3/10seconds. The trusted owner supplies issuer and actual lifetime-admitted native handlers; the router never opens workspace data or grants writer authority. This is not a deployable server, /api/me cockpit or complete epic acceptance.

POST /api/auth/mfa-enrollment/begin accepts only strict JSON {email,password}. No ambient session, supplied subject/issuer, remembered/trusted-device option or previous409 is authority. Native mfa_enrollment::begin revalidates password and current eligible access through the existing KDF/snapshot/writer protocol. Only known committed Setup yields200 {method:"totp",totpURI} plus the signed600-second pending cookie. Clear prior browser authority cookies before appending it. No session, backup-code disclosure or MFA-enabled event occurs. Issuer is trusted configuration; the URI account label comes from locked credential facts. A password-bound restart replaces old setup context while retaining native account failures/locks.

POST /api/auth/mfa-enrollment/confirm accepts only strict JSON {code} and the configured signed pending cookie. It calls only native enrollment confirmation, which requires its separate current enrollment namespace, unverified factor and MFA-disabled user. Login TOTP/backup cannot consume enrollment; a login challenge cannot complete setup. Ordinary session cookies and backup codes are not enrollment authority. Native current context, time, credential/access/factor/pool, attempt/account budgets and replay invariants remain unchanged.

Known committed Completed alone returns200 {status:true,backupCodes:[ten exact codes]} and a signed browser-session cookie without Max-Age. Native transaction ordering first enables MFA and revokes old sessions via existing trigger, then creates the fresh12h session, consumes context, accepts the TOTP step, resets counters and records telemetry. Codes are the exact current encrypted pool, disclosed once. Replay cannot disclose them again. Source bearer token is never returned in JSON. Wrong-code/replay returns401 INVALID_CODE, committed lock429 AUTHENTICATION_LOCKED; NotCommitted invalid_credentials uses401 INVALID_CREDENTIALS. Operational errors, OutcomeUnknown, wrong-profile handler cookies and JoinError return503 AUTH_UNCONFIRMED with no URI/codes/cookie, retry promise or rollback claim.

Shared human gates reject Authorization/service-key presence including empty/duplicates before cookie dispatch. Host/Origin/fetch/media/query, strict duplicate/unknown/null/typed JSON,8192-byte body and2-second body gates apply. Permit ownership spans blocking work after HTTP cancellation; cancellation does not roll back a started transaction. Process-local admission is not persisted/global/proxy/header/TLS/listener/shutdown qualification. Known-commit payloads contain intentional sensitive URI/code disclosure; response/parser/serde/browser copies are not universally zeroized. HTTP no-store/no-referrer/nosniff and no private payload logging remain mandatory; trusted owner logging/panic hooks remain its responsibility.

Retained LoginView enters the dedicated native path only for exact MFA_ENROLLMENT_REQUIRED with HTTP409. That clears the old password and requires explicit password reentry at begin. Existing BetterAuth session-based MfaEnrollmentView is unchanged. The native client uses one same-origin fetch per explicit action with no library retry loop, no redirect following and no caching; unlike BetterFetch, bare Fetch has no retry:0 option. Requests contain secrets only in JSON, never URL, storage or third-party QR services. Begin URI is validated for the native otpauth/TOTP6digit30second profile; React retains its Base32 manual key and presents a copyable read-only field, account/service and add-account/manual-key instructions. Password clears after every begin outcome. A known refusal stays generic; unknown begin explicitly says setup may have started and offers password-bound restart or normal login.

Wrong confirmed code clears input but retains setup and allows manual retry, restart or login. Lost transport, malformed acknowledgement or operational/unknown confirm removes key/password/code and the old form, explains setup may have completed and offers normal TOTP login. No automatic confirmation, backup regeneration or redisclosure is attempted. Confirmed success removes the setup key and displays all ten recovery codes only in component memory; no refresh occurs until explicit "Jeg har gemt koderne" acknowledgement. Leaving password/key steps is possible via "Tilbage til login", unmounting the secret state. Browser reload/closed tab/lost success can lose the only code disclosure; normal TOTP login reconciles completed MFA, and future separately authorized management is needed for new backup codes.
