# Native persisted email verification

This increment connects the native purpose-bound email token to one-time persisted issuance and an atomic application operation. The caller supplies an already admitted control connection, trusted workspace/current signing key, trusted Clock and audit key version. It does not enable an HTTP endpoint, send mail, migrate real data or qualify legacy dual writers. The full Rust epic remains open.

`issue` folds the address using the shared practical ASCII email policy. Connection preflight precedes input acceptance and reuse claims. Under an immediate control writer, it samples time once, signs a native token and persists only a SHA-256 bearer digest identifier in the existing verification table. The value binds the exact current subject/address/workspace, user creation/update and MFA flag, ordered credential rows with explicit NULL markers, and immutable credential/email/MFA/session-revocation lifecycle count. Credential rows are bounded and their sensitive strings zeroized where supported. Address verification is independent of workspace membership: it grants no role or access. Unknown and already-verified addresses create no intent and return internal None. Internal Some(token) is released only after a known successful commit. A public adapter must conceal account existence and must not expose this result directly.

`complete` receives the original bearer, never a previously verified proof. It begins an immediate transaction and samples trusted time only after writer admission. Signature, native purpose/workspace/active key and exact one-hour validity are reverified using that single sample. The digest must select exactly one persisted intent with exact issuance/expiry timestamps and unchanged context. Current email lookup must still resolve the originally bound subject, with emailVerified=0 and unchanged credential/lifecycle facts. Recycled addresses, changed/replaced credentials, changed user/MFA context, duplicate/corrupt intent, expiry and replay refuse. Updating and restoring a password still advances immutable lifecycle evidence and invalidates the link.

Success deletes exactly that issuance, sets only the subject's emailVerified=1 and updatedAt, and appends completion audit plus accepted verify-email telemetry in the same transaction. The existing trigger appends the email_verified lifecycle event. No account, factor, workspace access or session is created or changed. Other outstanding sibling rows may remain, but the verified flag and lifecycle change render them unusable. Existing sessions are preserved, matching the configured source behavior; no automatic sign-in is granted. All failures before commit roll back, and connection reuse requires successful rollback plus preflight. An uncertain commit returns OutcomeUnknown, retires the handle and releases no bearer or success result. SQL/claims/bearers never appear in public errors.

The process acceptance suite uses actual current synthetic control schemas and separate Rust processes in WAL and DELETE modes. It checks digest-only persistence, exact effects and protected-state preservation, replay/sibling refusal, exact restoration and NULL-to-empty replacement, address recycling, duplicate/corrupt rows, current facts after writer admission, single-writer serialization, SQL rollback, known/unknown commit and malformed input on unready handles. The GDD report proves structural readiness for this bounded application operation, not full feature parity or deployment authority.

Before enabling native send-verification-email/verify-email, implement the mail/redirect and HTTP policies, public generic acknowledgement, rate limits and caller/session checks. Close the legacy authoritative /verify-email bypass at the same enablement boundary: it accepts native JWTs but ignores persisted context. Native persistence cannot make that parallel legacy handler safe. Physical/lifetime writer admission, recovery-lineage qualification, service/provider parity, clients/distribution and all remaining epic acceptance remain required. Real mail and production changes retain their existing mandates.
