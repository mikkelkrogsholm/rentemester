# Native password-bound MFA enrollment ceremony

Provide an internal two-phase enrollment for an existing email-verified active workspace user with MFA disabled. Begin executes the existing password snapshot/KDF/locked-current-recheck operation and refuses enrolled users. It issues a private signed pending cookie and a source-compatible otpauth URI only after known commit, with no provisional authenticated session. Trusted runtime supplies cookie/keyring/clock/audit context and bounded issuer label; the account label comes from the locked canonical credential email, not a caller identity claim. This is a deliberate correction to source enrollment, which uses an existing session and reveals backup codes at enable time.

Generate a fresh32-character source-profile TOTP secret, encrypt it and a fresh unique ten-code default backup pool with the configured current key/OS nonces. Backup codes use the existing five-alphanumeric/hyphen/five-alphanumeric format and unbiased OS entropy with bounded rejection sampling. Sensitive owned strings/buffers/URI/code lists omit Debug/Clone/Serde and zeroize; caller/compiler/allocator/library/OS copies and whole-operation constant-time behavior are not claimed. Backup codes remain encrypted and are withheld at begin.

Store exactly one factor row with verified=0. Existing setup may restart only when exactly one row has strict verified=0; preserve its account failure/lock fields and refuse a future lock. Never silently adopt verified=1, NULL, duplicate or malformed factor state. Concurrent starts serialize; the later committed replacement invalidates every older setup context without resetting account budgets. No native TOTP replay row may already exist for an unverified factor. Bind a distinct enrollment context namespace/domain to the trusted workspace, current credential/access fingerprint, factor ID/encrypted secret/encrypted backup pool and immutable relevant lifecycle count. Use the existing bounded ten-minute challenge/attempt record shape, with no source in-flight adoption. Enrollment confirmation resolves only this namespace and strict user-MFA-disabled/factor-unverified state. TOTP and backup login resolve only the enrolled namespace and state; neither may upgrade an enrollment automatically or use backup codes to finish setup.

Confirmation holds one control BEGIN IMMEDIATE, samples trusted time once, rechecks current state/context and verifies TOTP. Five wrong attempts burn the ceremony; ten consecutive account failures across restarts lock for fifteen minutes. Reuse the existing strict expiry, counter, lock, duplicate, canonical current-schema/history/integrity and ordered-event exhaustion guards. Operational crypto/pool/SQL failures roll back without spending attempts; known wrong-code/locked rejections commit declared counters/telemetry. Require a valid current ten-code pool before successful disclosure.

On success, mark the exact factor verified, set user.twoFactorEnabled and canonical updatedAt, let the existing trigger record mfa_enabled and delete all pre-enrollment sessions, record the accepted TOTP counter, consume the setup challenge, reset account budgets, create a fresh twelve-hour session and append verification telemetry. All factor/user/session/replay/challenge/trigger/audit effects are one transaction. Create the fresh session after trigger revocation. Return its signed cookie and the exact ten backup codes only after known commit. A consumed challenge cannot disclose codes again. The legacy trigger actor system:better-auth is retained as a compatibility label and does not identify the executing runtime; accepted setup-start telemetry does not assert completed MFA.

A late SQL failure after actual success writes must restore old sessions, old factor/user flags, pending challenge, backup ciphertext and all trigger/replay/audit state. Every commit error reports OutcomeUnknown, retires the connection and withholds URI/cookie/codes; do not claim rollback or retry automatically. Lost begin responses can be recovered by another password-verified restart. Lost/unknown confirmation requires reconciliation and, if MFA completed, normal TOTP login; it grants no code re-disclosure or regeneration shortcut.
