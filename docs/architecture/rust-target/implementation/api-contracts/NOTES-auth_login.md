## Cookie and one-time disclosure policy

Known challenge/setup success first clears four profile-matched native cookies in order: session_token, session_data, dont_remember, two_factor, then appends a signed challenge cookie with Max-Age600. Known successful factor/enrollment completion similarly clears four then appends the **browser** session cookie without Max-Age/Expires. No bearer appears in success JSON. Cookie signature encoding and both profile templates are declared in the operation artifacts; no real secret examples are included.

Setup discloses a secret-bearing `totpURI` only after known setup commit. Native installed issuer is Rentemester; URI uses path encodeURIComponent-style escaping and issuer query form escaping, unpadded base32 of the generated raw32-character secret, digits6/period30. An explicit fresh password-bound setup restart replaces an unverified secret and encrypted backup pool. It is not idempotent or a readback of the first URI; an already-enrolled account is denied.

Enrollment completion enables verified MFA, revokes previous sessions via the canonical user-update trigger, records the TOTP step, consumes the challenge and issues a new session atomically. Exactly ten distinct case-sensitive backup codes are disclosed once with status true. Lost output is not recoverable by replaying the consumed enrollment challenge. These endpoints do not return backup codes from session read or an enrollment secret from confirmation. Separate password-authorized backup-management operations are outside this partition; their existence is not a replay guarantee here.

Factor success consumes all three pending challenge/attempt/context verification rows and commits a new session with audit. TOTP records durable highest accepted step (30-second step, adjacent-window crypto verification); repeated accepted step is rejected. Backup success atomically replaces the encrypted pool without the used code: irreversible after commit, never a retry token. Invalid attempts commit counters; five rejected attempts burn the challenge; ten factor failures lock the account for15 minutes. ## Retry, unknown outcomes and cleanup

No operation supports a request idempotency key, key TTL, scope or tombstone. Those values are null, not fabricated original-key retry promises. Only session GET is classified automatically repeatable (still rate limited). Explicit HEAD is refusal, not a useful retry/readback operation. Mutating auth requests must not be blindly replayed while pending or after unknown commit. A new password flow, a new current TOTP/unused backup code, explicit setup restart and cookie cleanup are distinct actions.

Authoritative current readback is GET `/api/auth/get-session` with the actual profile/workspace cookie jar. Adoption checks user.id, canonical email, session.userId and expected session.id where known, plus verified email/MFA. `/api/me` independently checks current access. Null proves only no currently usable authenticated session for that cookie; it cannot prove absence of an undelivered committed session, pending challenge, other sessions, or server credentials. No claim that missing cookie means transaction rollback.

Sign-out with a valid signed bearer calls native sign_out, deleting exactly its token/session row if present and auditing that deletion. An already absent row is a successful zero deletion; this natural absent-row behavior is not response replay storage. With no valid MAC proof HTTP skips native revocation entirely and returns success plus local clear. The latter clears a pending challenge cookie in memory/browser but **does not burn durable pending challenge rows or revoke an undelivered session**. Unknown sign-out can be reconciled with retained original valid bearer/current readback; explicit repeat deletion is meaningful only for that same retained bearer. It does not revoke every session or provider credential.

The shared React `LoginAttempts` fence is a client consumer comparison, not the HTTP producer or an SDK-schema substitution. It serializes cookie mutations; cancel waits for pending mutation settlement, calls signOut with retry0, then requires getSession SDK result data exactly null and no error before unblocking credentials. Failure remains blocked. `assertSession` checks selected canonical email/user identity and verified MFA before adoption. Raw HTTP `{success:true}`, `{status:true}`, challenge/setup bodies and null remain distinct; no silent envelope normalization is specified here. Aborting a client request or clearing React memory is never evidence of native cancellation/revocation.
