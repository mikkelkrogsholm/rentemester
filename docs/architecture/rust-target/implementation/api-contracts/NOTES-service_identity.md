## Authority and wire boundaries

POST requires exact Origin/Host and JSON content type; GET permits absent Origin but validates one if supplied. Fetch-site restrictions, observed peer, shared lifecycle cooldown budget (10/60s), profile-bound HMAC session cookie, current/fresh session and current native verified owner authorization all remain binding. Authorization/service-key headers are refused rather than used as fallback. All POSTs, including recovery, require a session less than ten minutes old, `confirm:true`, active transfer mode and the same serialized native control writer fence. List only requires a current session; it rolls back its read transaction and validates rollback before returning. Role is the latest access-event role, not stale cookie data. No revision/If-Match support or embedded grant authority is invented.

POST schemas distinguish absent optional values from explicit null. `expiresInSeconds` uses serde u64 syntax and bounds (one day through one year), defaults to 90 days, and does not appear in issuance receipts. UUID lookup trims surrounding Rust whitespace and ASCII-lowercases; version 1–8 and RFC variant are validated, rather than accepting arbitrary UUID-ish strings. JSON Schema patterns express the shape; accompanying native parser constraints specify Rust Unicode whitespace, UTF-8 byte bounds and Unicode scalar/control semantics where standard JSON Schema character counts are insufficient. Unknown and duplicate recognized JSON fields refuse. Any query (even empty) refuses on GET/POST; HEAD's closure ignores it. GET accepts no body bytes, not even whitespace. Body limit 8192 and two-second read timeout apply after admission/proof/capacity; overflow/read failure and timeout have distinct statuses.

Inventory is a real principal DTO, not issuance DTO: principal ID, display name, original created timestamp, count and credential list. Credential has only ID, enabled boolean-or-null and expiry string-or-null, never plaintext secret, key hash, marker, prefix or operation ID. Created timestamp can retain a validated legacy SQL timestamp rather than normalized ISO output. The active count includes NULL enabled and does not subtract expired keys: it is not a current effective-access count. Principal ordering and binary ID ordering are explicit; bounds fail closed rather than silently paginate/truncate.

## One-time issuance, stable identity and uncertain outcomes

Create/rotate return only `ok`, canonical operation ID, service-account ID, credential ID and one-time 68-character secret after known commit. Create is 201, rotate 200. Rotation disables the old credential in the same transaction. Revoke is 200 with `ok`, operation ID and `revoked:true`; it does not return a principal DTO or secret. The newly generated key's insert configures provider-independent native rate-limit metadata; this endpoint does not expose those fields or grant company access.

`operationId` is stable correlation/collision protection, **not an idempotency replay key**: same-operation create/rotate/revoke returns 409 `OPERATION_REUSED`, not the original receipt or plaintext. There is no TTL/replay-cache/tombstone promise. Prefer a caller-retained operation ID for reconciliation; if omitted, the generated ID is known only from the receipt. Display name is not unique and cannot safely deduplicate an unknown create.

Recovery is an explicit confirmed mutation with current fresh owner authority, not a secret-fetch read. It returns all seven documented fields, including nullable credential/replacement IDs. Completed history returns `recovered:false`; already recovered returns true; a recently recovering legacy record (<30s) returns recovering/false without resolving it. Recovery of revoke disables its target if still present and appends completed; recovery of interrupted create/rotate disables matching provider-marker keys, appends failed if necessary then recovered. It does not restore a rotated old key or mint a replacement. Completed create identifies credential and replacement with the same ID; completed rotate preserves old credential ID and a distinct replacement. Current native mutations append pending and completed atomically; legacy nonterminal histories are retained and validated, not falsely described as new native external provider calls. Failed legacy provider state alone never proves credentials disabled.

After a lost/malformed successful create/rotate/revoke response or AUTH_UNCONFIRMED, do not blind replay. Use retained operation ID with recover and authoritative inventory IDs, not a name match. Recovery/list can never recover plaintext. A completed issuance with lost secret requires explicit reconciliation and new confirmed rotation/new operation ID (and revocation as appropriate), not automatic redisclosure. Missing history is 400, not a durable absence receipt. Inventory absence is not proof of no commit. get-session read-back establishes current session/user authority only, not lifecycle commit; changed/expired session needs explicit authentication/authority restoration before reconciliation. No generic original-key retry, automated new-key issuance, or silent cancellation rollback is promised. HTTP cancellation does not cancel blocking work: the permit remains held through completion. Client-memory cookie cleanup would not itself revoke durable credentials.
