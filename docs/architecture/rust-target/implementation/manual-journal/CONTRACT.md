# Pure manual journal validation

Continue R09 toward the shared posting pipeline by implementing pure manual journal validation, exact nominal row/account references and explicit rule-version binding. Base:138cee53a6fbe7e538ed1dbbda37d31cfc819161. This does not enable a writer or change existing TypeScript validation, persisted data/hash bytes, historical import/reversal privileges, authorization or release gates. Main owns engine identifiers/rules/journal modules, CLI fixture adapter, development harness, scoped contract/model/evidence and implementation progress. Stop at verified manual preflight plus independent review; full epic remains active.

Input is a typed canonical Date, required text, canonical Currency, optional exact document/bank IDs, optional two-decimal Money/positive six-decimal FxRate, optional program marker and ordered lines of account reference, default-zero Money debit/credit, optional VAT code/text. Canonical wire strings must be used for exact money/rate/IDs; numbers, fractional/exponent/noncanonical ID strings or signed64 overflow refuse. DocumentId, BankTransactionId, JournalEntryId and PeriodId are distinct types covering the full SQLite signed64 range including zero/negative existing keys. Absence is Option, never truthiness. AccountNo is an opaque nonempty string with no digit/range/trim/Unicode/default assumption; actual existence and semantics come from local facts, never a hardcoded company chart. Raw ingress/default normalization and transport byte budgets remain adapter duties.

Trusted facts are explicit, caller-supplied snapshots: request transaction date, latest allowed transaction date resolved by the clock/config adapter, account activity/type/VAT-control/settlement semantics, existing documents and any prior credit-note journal number, banks and existing reconciliation links, and candidate accounting periods with replayed effective state. Facts must match the request date; duplicate account/document/bank/period identities or invalid period ranges refuse as invalid_context rather than silently replacing rows. Period audit replay and fact collection are not implemented here. These facts are not accepted as client assertions by any product endpoint. Future application wiring must collect/revalidate them under the actual admitted writer transaction and stable workspace/company identity; pure ok grants no authority or reservation.

Manual rules must reproduce the current ledger checks on supported typed values: nonblank text using ECMAScript trim whitespace, at least two lines, reserved historical-import marker refusal, existing/active accounts, nonnegative exactly-one-sided nonzero rounded lines, known VAT codes and explicit income/expense VAT base marking for VAT controls (except pure VAT-control/settlement transfer with a settlement), exact debit/credit equality, required existing documents for expense/income, single credit-note journal, and existing/unreconciled source bank references. Unknown accounts skip subsequent line-specific checks/sums as in the legacy source; no default account VAT code is treated as explicit evidence. Negative/sub-cent signed zero follows typed Money quantization before validation. Any errors mean refusal; invalid context/rule version yields no validation result.

For non-DKK entries require positive foreign/DKK amounts and a positive FxRate, then require exact amountDkk == FxRate.apply(amountForeign). This uses explicit prequantized two/six-decimal operands; legacy Number binary intermediate/bridge differences are fixed corpus corrections, not normalized away. DKK ignores optional FX evidence after typed construction, matching existing validation scope; providing malformed typed metadata still refuses at decoding. No claim that FX header amount equals gross journal movement, that a quote is authorized, or that this validates invoice evidence/settlement/posting-side state is introduced.

Date checks compare canonical Date values to the explicit latest allowed date; periods are considered in period-end then exact ID order and only the first overlapping effective closed/reported period blocks. Reopened/open facts do not block. Period kinds/status/reference messages retain current source behavior; only known period kinds and effective states are representable. There is no wall clock, environment read, SQL, lifecycle replay or default45-day configuration inside the engine.

Rule metadata is supplied as parsed named bundles, versions and declared rule IDs. Compose the canonical complete version string by sorting bundle names and joining name=version with semicolons, independent of input order. Reject duplicate/empty/noncanonical names/versions/duplicate rule IDs and absent required rules. Bookkeeping dk-bookkeeping-v0.0.8 and VAT dk-vat-v0.0.5 are the only implemented manual-policy versions; unknown versions fail as unsupported_rule_version. Other bundles are recorded provenance only and not claimed executed. Require exact caller expected-version equality to reject stale preflight as rule_version_mismatch. Preserve supported manual VAT code vocabulary explicitly; do not pretend this implements arbitrary YAML machine rules, legal-source verification or other bundle algorithms.

Return deterministic ordered typed violations (code, field and message), exact debit/credit totals, bound complete rule version and the required legacy rule IDs. APPEND_ONLY is a required storage invariant reported separately, never an invariant proven by pure validation. No posting token or mutation command is returned. Expected business refusals accumulate in legacy order; malformed types/context/rule configuration fail before evaluation. ECMAScript whitespace includes BOM and excludes U+0085; do not substitute Rust trim semantics.

Acceptance: fixed independently authored synthetic expected cases cover balanced/unbalanced/one-sided/negative/round-to-zero/large exact sums, arbitrary account identifiers, VAT branches/codes, document/credit-note/bank referential conditions including zero/negative/full-width IDs, period overlap/reopen/order/future dates, manual marker, FX rounding corrections, rule sorting/duplicates/missing/unknown/stale versions, strict serde and context completeness. Run actual unchanged TypeScript validateJournalEntry on a disposable synthetic canonical database populated with the same facts, compare supported numeric-domain cases and freeze every deliberate typed/correction difference; exact expectations must be fixed independently before invoking either engine. Verify every native result against the fixed corpus, preserve source bytes/rowcounts after validation, and verify deterministic repeated runs. Run scoped GDD readiness before implementation; engine dependency/I/O boundaries, formatting/Clippy, prior suites, targeted source tests and independent review must pass. Artifacts bind source hashes and report unsupported environments honestly.

Limitations remain: source facts/provenance/clock collection, lifecycle replay, transaction/authority/revocation/idempotency/write fencing, actual posting/reversal/import/invoice evidence, broader rule evaluation, full R01/R03/R09/R12 acceptance, server/CLI/MCP/web/GPUI, distribution and cutover. No real company data or policy instance is checked in or mutated. Historical rows with different representations need explicit adapter/adoption decisions, not silent ID/schema rewriting.
