# Native HTTP password-bound backup-code management

Expose POST `/api/auth/two-factor/view-backup-codes` and `/api/auth/two-factor/generate-backup-codes` through an explicitly injected optional native handler. The handler receives only runtime-bound current-session proof, a zeroizing password and a typed View/Regenerate operation; it maps to the existing admitted native application transaction. The JSON body accepts no caller user ID, email, factor ID or raw bearer; authority comes only from verified cookie plus password and current native transaction facts. No workspace path, data opener or writer grant comes from HTTP. Without a trusted handler both routes return404, with no legacy fallback. The serving owner must retain physical/control/workspace lifetime admission and retire unusable handles; independently running legacy writers must be drained and exclusively routed before real enablement. This increment performs no production enablement.

Both routes require configured Host/Origin, same-origin-compatible fetch-site, JSON without content encoding, no query and a strict signed session cookie from the configured workspace/profile. Service/mixed credentials, duplicate Cookie headers, bare/duplicate named session fragments, pending-factor proof and wrong signatures refuse before native dispatch. Accept only a JSON object with exactly one string password; arrays, missing/null/duplicate/unknown fields and subject selectors refuse. Password bytes are preserved and bounded by the existing4096-byte KDF input limit. Request body is bounded8192 bytes/2seconds. View and regeneration share one direct-peer3/10second bucket and the same four blocking-worker capacity as identity/recovery; permits remain owned by blocking execution. Forwarded headers and operation rotation cannot change rate identity. The common429 response conservatively retains Retry-After60 even for this shorter bucket. Rate state is process-local; distributed/proxy/TLS/listener/shutdown/logging remain separate qualification work.

The existing application keeps password KDF work outside the writer lock, fences the captured credential/session snapshot again under BEGIN IMMEDIATE, samples trusted time at final admission and requires current session younger than ten minutes, verified email, enabled/verified MFA, active workspace membership and one canonical local credential/factor. View decrypts the strict remaining encrypted pool of zero through ten codes and commits its management audit. Regeneration validates the old pool, atomically replaces it with ten fresh unique canonical case-sensitive codes encrypted under the current key, and commits its audit. Other factor fields, session rows, credential facts and TOTP replay context remain unchanged by management. Real deletions/consumption during subsequent login are separate operations. Exact transactional and concurrency invariants remain in [the native management contract](../backup-management/CONTRACT.md).

Only known native commit returns200 `{"status":true,"backupCodes":[...]}` with zero through ten codes for view or exactly ten for regeneration. Response uses no-store/no-referrer/nosniff JSON and sets no cookie. Sensitive output keeps the existing non-Debug/non-Clone/non-Serde zeroizing list until post-commit serialization; the HTTP body necessarily carries plaintext codes to the authenticated client. Wrong password/current authorization returns401 INVALID_CREDENTIALS; operational/schema/crypto failures, unknown commit, panic or an unexpected short regeneration result return503 AUTH_UNCONFIRMED without codes, session or claimed success. Confirmed operational rollback is atomic. An unknown commit withholds output but does not assert unchanged pool/audit; the handle must be retired and results reconciled by a new fully authenticated view. No automatic retry is added.

Installed Better Auth's generate endpoint uses the same path and success shape, but lacks the native credential/session fencing and management audit. Its `viewBackupCodes` is a server-only helper taking a userId, not an HTTP/client method. The new password-/Fresh-session-bound own-view endpoint is an intentional native extension, never exposure or forwarding of that helper. Canonical default encrypted pool crypto remains interoperable with the installed source. UI reports unsupported404 explicitly and never falls back to a userId helper or automatically regenerates.

The retained React account menu opens a dedicated Sikkerhedskoder dialog keyed by authenticated user/current-session ID. Opening it makes no request. Viewing requires a freshly entered password; replacement additionally requires explicit confirmation warning that old codes stop working. Both raw same-origin client requests carry password only and explicit retry0. The UI validates status exactly true, canonical unique code strings, remaining count at most10 and regeneration count exactly10 before disclosure. Empty view is valid exhaustion, not fabricated recovery codes. Missing/false/null/malformed/error/transport regeneration results reveal no codes and explicitly warn that previous codes may already have been replaced; the next action is an explicit password-bound view, never automatic replay.

Passwords clear when a request starts, and password/code/confirmation state clears on close, unmount, pagehide or hidden document. An epoch guard discards late responses after hiding/unmount; an in-flight hidden regeneration leaves explicit unconfirmed guidance. Codes stay only in the active component/DOM and are not written to URL, storage, clipboard or logs. JavaScript/network/browser memory cannot be securely erased by clearing React state; this is bounded UI disclosure, not a memory-erasure or deployed browser-security claim. Dialog controls retain existing modal focus/confirmation behavior; a known unsupported view leaves a fixed server-availability message.

Acceptance uses canonical synthetic WAL/DELETE controls, real native HTTP sockets, installed source-signed cookies and source crypto to compare existing/replaced pools. Tests assert exact management audit, preserved unrelated factor/session facts, old-code INVALID_BACKUP_CODE refusal and new-code login/remaining-nine disclosure, consumed/empty pools, strict pre-dispatch/body/credential refusals, stale/disabled/unverified/revoked/current password refusal, malformed pool, actual DELETE commit-busy withholding for view and regeneration, shared direct-peer KDF rate and absent-handler refusal. Socket unit tests cover HEAD/query/duplicate Cookie/array no-dispatch and failure/unknown/panic/short-success withholding. React tests cover confirmation, strict ACK/pool validation, unsupported/no-fallback, clearing, hidden late-response discard and no replay. Actual installed-client probes record request encoding without secret values. Separate mocked React and native/source sockets do not prove a deployed browser journey. No real data, external mail, live legacy closure, provider/service/API-key/trusted-device, remaining password-management HTTP, complete physical/lifetime/restore admission, CLI/MCP/GPUI/distribution/cutover or whole epic completion is qualified.
